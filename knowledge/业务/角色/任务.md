### 任务目录、固定主线与奖励事务

当前QH/QT目录包含204个可购买卷轴、217个任务和357个目标。QH目录之外的13个任务组成固定主线 `71000000..71000012`；教程完成后，C59B在固定类型1槽位恢复首个未领取主线任务，并保留已有主线行。普通购买任务使用十个类型0槽位。

- 目标路由覆盖地宫通关与多次通关（2/20）、家具摆放（5）、组队通关（9）、收徒（11）、零收费／零道具／零复活限制（21/22/23）、单人及指定宠物／BOSS通关（25）、怪物命中（26）、带等级门控的技能成功（35）以及合成宠物／卡片持有（37）。
- 类型21/22/23在实时结算时按本轮 `Charged`、`ItemUsed`、`Revived` 状态判定；条件类型14保持明确的未归类状态。

- 任务进度持久保存，多目标通关分别记账；多目标任务的 Progress3 保留已完成子目标的累计数，只有全部子目标完成时才将 Progress1 置为可提交。
- 客户端切换当前条件依赖 State3，而不是 Progress3；评估事务将 State3 投影为目录顺序中首个未完成目标的零基索引，全部完成时保留最后一个有效索引，不发送越界值。
- C59B重新评估时会修复旧行的索引，保留已有逐目标通关记录；若旧账本先完成后面的地宫，也仍指向最早缺失目标，不凭总数跳过它。
- 结算提交episode、dungeon-bit、score、pet、solo-or-party及BOSS状态；技能与复活在本地事务或工作进程确认后提交；怪物命中使用QT目标代码。
- C59B是任务列表计算与返回边界，统一评估等级、库存、卡片、家具和师徒状态。
- 字段及客户端目录选择链归[任务窗口与交付边界](#kb-08-069)，候选发布和实机验收状态归[验证入口](#kb-09-001-2)。

- 任务交付使用单一数据库事务：校验已开始且由适配器评估的任务行，发放Hans、EXP、普通／家具域物品和卡片，应用真实等级、经验和基础HP/MP成长；力量／体力／敏捷／智力／幸运及未分配点仅保留旧档值，不发放虚构属性，记录主线领取与任务标志，删除已完成任务并插入下一条主线。
- 重复提交复用已提交结果，保持单次发放语义。

- 主线 `71000000..71000011` 使用精确奖励元组 `type=8, code=0, amount=1`，`71000012` 作为链尾。
- 完成带勋章奖励的任务时，C59A完整帧 `WORD +0x10` 写1；终章未兑奖时持久数量等于已提交的主线勋章领取数，C354通过C355完整帧 `BYTE +0xF3` 恢复该值；终章已整包发奖时恢复已兑换哨兵100，规则见[终章兑奖](#哈希奥终章礼包)。
- C59A之后按同一请求边界返回C59C刷新。

### 哈希奥终章礼包

#### 原版机制与数值边界

- 原版 `QS._D31` 文本10028要求携带12枚勇者勋章找地宫门口的哈希奥；10026明确以12枚勋章交换礼包；10027为“哈希奥的大礼包1个”。`GQ._D32` 引导6关联奖励文本10027。
- 客户端 `0x527A90` 在入口值49且本地勋章字节等于12时进入终章；`0xA59A20` 展示10026并经 `0x402E00 → 0x4D5460 → 0xADA3E0(0,frame)` 提交 `C599/88`，载荷 `WORD +0=7`、`WORD +2=0`、`DWORD +4=6`，72字节尾区不解释为奖品。
- `0x4D7A00` 构造opcode和长度；`0x4D34D0 → 0x4D56A0 → 0xA14900` 在引导状态22消费 `C59A/36`。成功要求完整帧 `BYTE +8=0`、`WORD +16=7`，奖励窗口经 `0x41AAA5 → 0xA5AB70` 读取引导6的奖励文本；确认后 `0xA59A20 → 0x41DF98 → 0x4D7C60` 将manager `+0xCC` 写100。100是已兑换状态，不是勋章数量。
- 完整帧 `BYTE +9/+10` 分别触发物品／金币与卡片状态刷新；最大HP／MP及经验读取至DWORD+32，保持36字节安全长度及既有有效资源上限约定。终章拒绝使用结果3的恢复性提示，不使用会进入退出状态25的结果1；失败尾区清零。
- 上述链路已与现用客户端对应函数逐字节核对，原始输出见[静态调用链](../../evidence/static/hasio-reward-20261013/static-chain.json)与[勋章入口](../../evidence/static/hasio-reward-20261013/medal-gates.json)。静态证据证明兑换流程和文本，不证明礼包原版内容，也不证明必须存在独立可开箱物品。

#### 当前项目奖励与事务

- `HasioRewardPolicy` 明确采用项目策略，默认一次性增加10000 Hans、10份 `14002486` 伊露卡灵丹妙药、5张 `12000002` SP+2卡片；这不是已证实的官方奖品配方。直接发入钱包、游戏道具背包和卡册，不新造礼包物品或改写原版资源。
- 兑奖要求活动角色／世界会话授权、教程及尼莫引导完成、`71000000..71000011` 的12条持久领取记录。链尾 `71000012` 的奖励事务独立，不用客户端自报进度或请求尾区绕过资格。
- `CompleteStoryGuideAsync(type7,id6)` 在单一SQLite写事务内整包发奖、保留并重映射已有快捷栏索引、将终章 `RewardPending` 写0。游戏道具84行容量、每种SP卡255张容量、整数钱包溢出及每次库存写入均检查；不能整包发放时全部回滚，不返回领取成功，也不截断数量。
- 发奖成功后，同一请求返回 `C59A`；新增游戏道具时随后返回 `C430/C379`。卡片有增量时C59A完整帧+10置1，后续卡册仍经正常 `C3E7/C3E8` 请求刷新，不额外推送其他页的卡册。
- 已提交且 `RewardPending=0` 的记录重复应答成功，不重新发奖；之后的配置修改不改变已领取结果。旧版 `guideId6/RewardPending=1` 在C354恢复时不投影终章完成位，保留12枚勋章；玩家再次找哈希奥才补发并原子清除欠发标记，不在登录时自动送包。
- 实现入口为 `HasioRewardPolicy.cs`、`DatabaseService.HasioReward.cs`、`DatabaseService.cs` 及C599路由。构造检查使用 `--hasio-reward-self-test`，同时纳入 `--quest-system-self-test`；原客户端新包领取画面尚未验收，受测身份见[验证状态](../../工程/验证状态.md#哈希奥终章奖励验证)。

#### 配置

可选UTF-8文件 `hasio-reward.json` 放在实际 `game.db` 旁；缺省使用上述项目默认值，每次未完成兑奖读取一次。严格接受以下字段，拒绝重复／未知字段、重复代码、空奖励、越界数量、超过64 KiB的文件及非支持目录项。`Items`仅支持现有永久、可快捷使用的游戏消耗品，`Cards`仅支持现有SP卡；配置存在但无效时拒绝兑奖并保留资格，不静默回退默认值。

```json
{
  "Version": 1,
  "Hans": 10000,
  "Items": [{ "Code": 14002486, "Quantity": 10 }],
  "Cards": [{ "Code": 12000002, "Quantity": 5 }]
}
```

### 目标分数任务：资源与当前适配器判定

- QT/QS的“获得目标分数/Epi 1..16”对应任务`70000071..70000086`、目标`75000217..75000232`。
- 每项type25、target1、count1；tag12/comparison1指定Epi，tag16/comparison0指定分数。
- 门槛依次为5000、15000、55000、90000、220000、270000、360000、420000、630000、750000、820000、1000000、1100000、1200000、1300000、1450000。
- QS文本10093..10108描述对应Epi的地宫分数目标，任务条件维度为Epi和分数。

- 当前适配器采用单次成功结算策略：`QuestCatalog.MatchesSettlement`比较当次episode与`score >= threshold`，`DatabaseService.EvaluateQuestObjectivesAsync`要求任务已开始且HasClear。
- 每次输入独立判定，达标后在`CharacterQuestObjectives`持久化完成标记，任务刷新与重登继续保留完成状态。
- 该分支适用于各组队及难度配置，以本人输入分数为准。
- 托管CF87入口采用基础`score`（击中＋首领），原生CF88入口采用个人`completed.Score`（最终结算分）；关系加分按各入口的上述口径处理。
- 战斗分数账本随新阶段重建，局内经验high-water账本独立维护。

- 任务构造与持久化验证覆盖：Epi1门槛5000时，先后输入3000、2000仍为进行中，单次成功结算5000转为完成；成功状态、Epi匹配和主动结算共同决定完成资格，重复达标幂等，数据库重开后保持结果。
- 多目标主线 71000006“新的挑战”关联 75000144／75000145／75000146 三个 Epi3 地宫目标；累计进度为1、2、3，State3分别切换至1、2、2，全部完成才允许交付。
- 构造检查直接读取C59C固定主线记录的索引字节，并验证旧档已完成地宫1和3时指向地宫2、重复刷新幂等、重开保持、补完地宫2后可提交。
- 验证层级为当前适配器策略的字段构造与持久化。

### 任务窗口与交付边界

- 当前契约为 `C59B/8 -> C59C/252`、`C599/88 -> C59A/36` 和 `C59E/12 -> C59F/24`。
- C59C载荷以DWORD普通任务数开头，随后容纳十条20字节普通任务记录；载荷 `+204` 为固定类型2槽位，`+224` 为固定类型1槽位。
- 每条记录承载active、state、type、state3、三个进度字段和任务ID。

- C59C处理函数 `0x4D5ED0` 从完整帧+232读取固定主线记录，经 `0x402FF9 -> 0x4D8D50` 应用。
- `0x4D8D5C..0x4D8D64`读取记录BYTE+3（State3），调用 `0x408DF5 -> 0x4D8E30`；`0x4D8E3D`将其写入任务对象DWORD+4，`0x4D8E4D`经 `0x416E78 -> 0x9901B0`以该值查QT目标数组。
- `0x9901B0`要求索引小于目录目标数并返回数组+8×index，越界返回0；`0x4D8E52`直接解引用所得目标ID，再经 `0x40BE5B -> 0x98FE90`查目标定义，写任务对象+0x14。
- 因此该字节是零基当前子目标索引，不是布尔完成标志，全部完成时也必须保留有效末项索引。
- 记录DWORD+8（Progress3）在 `0x4D8D50`另写对象+8，不能代替目录选择。
- 当前目标索引与累计进度分别维护，业务策略归[任务目录、固定主线与奖励事务](#kb-03-048)。

C599载荷 `+0..+7` 是稳定任务元组：WORD任务类型、WORD运行状态、DWORD任务ID；其余72字节按不透明保留区处理。C59F状态位于载荷 `+0`，成功时64位Hans余额位于载荷 `+8`。

- C59A完整帧 `WORD +0x10` 是完成类型选择器。
- 客户端处理函数 `sub_A14900` 在 `0x00A14937` 读取该字段，在 `0x00A1493E` 分离类型7，并在 `0x00A14A04..0x00A14A0D` 分离零值与非零值。
- 固定主线由QT精确奖励元组 `type=8/code=0/amount=1` 选择类型1。

- C355完整帧 `BYTE +0xF3` 是持久主线勋章载体：`0x0053110D..0x0053111D` 读取该值并调用thunk `0x0041DF98 -> sub_4D7C60`，将字节写入manager `+0xCC`；`sub_4D7C80` 读取同一状态。
- 数值由适配器已提交的主线领取账本提供。

C59B是任务窗口刷新请求边界；适配器在该边界返回C59C，并在已初始化的非战斗村庄／商店场景内按同一请求附加C59D。战斗进度持久保存在任务账本中。完整玩法归属见[任务目录、固定主线与奖励事务](#kb-03-048)。

### 验证记录的版本边界

- 多目标主线按QT当前目标索引切换条件，逐目标保存完成状态，并在刷新时修复旧档索引。
- 任务专项覆盖地宫1、地宫2、地宫3与交付，验证层级为适配器构造和数据库事务。
- 字段语义归[任务窗口与交付边界](#kb-08-069)，评估与旧档修复归[任务目录、固定主线与奖励事务](#kb-03-048)。
