## 房间身份与重新入房

准备房的房主UID及成员槽位由活动队伍确定，成员进入顺序与传输连接复用均保持同一身份。内部F109/20携带角色UID、房主UID和槽位三个DWORD；槽位0对应房主，成员使用1、2。入房身份、成员列表、出生位置、加载屏障及三槽评分统一使用该映射。成员列表中的房主发生变化时，已有成员收到包含自己在内的完整列表。地图准备同时为全部成员设置实际／显示阶段、关卡、难度和加载周期，情侣药效共享使用相同的关卡身份。

### 组队续关与观战

<a id="kb-05-006-2"></a>

<!-- BEGIN 05-006-2 -->

阵亡成员保持接收房间更新的观战状态，主动道具、技能和拾取按死亡状态限制。最后一名参战者提交失败结果且全队生命归零时，同房已阵亡观察者同步进入失败结算；各角色结果按会话、战斗周期及结算周期单次发布。失败页面允许阵亡角色直接返回城镇，重新挑战仍使用原有显式授权。

下一地宫动作由当前房间的一位发起者授权。同房同关卡组员共享该动作的确认，保留过渡期连接，并以各自战斗周期校验状态更新；并发继续保持一个房间动作，拒绝时恢复组员原授权。每次有效续关同时更新所有活动成员的地宫、实际阶段、显示阶段和难度，重置上一场的加载屏障及最终开始确认。队员的连接局部状态在后续请求前切换到新关卡准备阶段，队长取得关卡资料时为队员建立新的预加载周期；队员通过自己的资料请求或对应房间初始化完成加载。当前成员的CF70资料刷新保留已下发的预载授权，成员退出、新入房与连接代次变化分别清理授权。离场、断线及连接槽位重新分配按成员代次清理续关状态。当前续关仅在本房存在已观察到CF99的有效连接时执行前置清理，而且只对标记成员发送CF6D，再向活动成员发送CF8C；正常存活续关及没有CF99的死亡重试均不重新触发首次入房。CF99掩码在连接复用、房间创建及离场边界清理，成员离线／离房不触发或接收前置清理，一个成员的CF99不能重置未标记队友。CF6D的成功状态为BYTE+8，独立BYTE+9按当前房间身份写房主1／队员0，DWORD+0x10使用当前房主UID，本地角色UID使用既有身份；托管成功门控只读BYTE+8，成员仅在房间续关授权下接收该初始化，队员发起时被标记的房主仍可收到+9=1。CF6D会额外发起首次入房P2P／成员资料流程，不得把它当作通用、无副作用的续关初始化。本人主动CF70对应的本地CF71结束过渡离场保护。新阶段中的阵亡成员恢复生命、魔法和战斗状态，资源冻结持续到对应加载初始化；保留控制器的CFEB／CFEC续关维持已建立的情侣用药身份。掉落与评分的角色归属由[本主题对应章节](关卡与房间.md#kb-07-006-3)维护。

### 连续挑战的初始化与战斗控制器生命周期

正常连续挑战使用CF8B mode2与CF8C结果重载链，重试／挑战超级Boss使用mode1。CF6D对已收到CF99的成员定向发送并清理返城状态；其CFD1/CFD2与CF8C重载各自触发C587/CF70。适配器在每次有效续关开始时为活动成员重置资料合并状态，为实际发送CF6D的成员启用一次性合并：第一轮CF70发送完整名单；第二轮保留本人的CF72、全部队友CF71及准备状态CF7E，并复用第一轮本人CF71完成的位置初始化，然后解除合并。后续显式刷新、其余队友及房主变化的完整名单推送保持原行为。新续关／新房、离场和连接复用清理旧合并状态，以成员及房间生命周期决定合并资格。CF71本地分支直接写坐标：槽位0的初始Y为252，入场目标Y为151；单次本人坐标初始化保持入场位置与座位字段连续性。地址与字段边界归[本主题对应章节](关卡与房间.md#kb-08-023-1)。

成员离场采用完整清理路径，正常续关采用结果重载路径。验证覆盖UID4单人三轮worker加载、P2P先到／结果重载先到的两种请求顺序、双人普通／超级地宫三轮、CF99成员隔离、第二轮队友／资源／准备状态保留、本人坐标单次初始化、资源恢复、S2C序列环、checksum及request-low。该范围为适配器状态机构造与工作进程集成；客户端联合验收范围归[本主题对应章节](关卡与房间.md#kb-09-021-3)。

槽位0入场位置为`(77,151)`，重复执行本地CF71会将其重写为`(77,252)`。结果页发布时旧战斗控制器可处于state9／退出动画state2；该退出动画的清理会关闭world运行位并将控制器转回state1，而应用页面可仍为战斗页4。连续挑战在结果重载边界复位旧控制器，使新关开场沿独立生命周期运行。

CF88兼容入口直接发布结果页后，旧战斗控制器的终局状态可能跨地图保留。当前实现把原生reset放在合法CF8C的普通结果重载边界：mode0/1、结果页6、目标state7且旧实例存在时执行，然后调用原重载。CF8C维持48字节合同，角色及HP/MP/P沿既有资源恢复链处理。位点、字节、调用约定及安装步骤归客户端二进制补丁文档。验证覆盖3项客户端迁移、160种控制条件组合、5轮原指令隔离及8项worker续关检查；发布及客户端验收范围归[本主题对应章节](关卡与房间.md#kb-09-021-3)。

### 活跃房间与诊断隔离

一个native worker内的Boss上下文由`multiplayer_shared_boss_context()`共享，不能把新连接等同于新房间。无当前房间资格的连接不得在已有成员的RUNNING／TERMINAL战斗中执行CF6C、CF70、CF77或CF7F：这些请求在任何成员登记、地图选择、共享账本重置和名单广播前被消费，不发送CF6D／CF71／CF72／CF80；已在房间的成员及正常战前加载仍走既有边界。当前实现采用此门控，发布归[本主题对应章节](关卡与房间.md#kb-09-021-3)。

`DungeonSaveChecks`通过`NativeDungeonPool(usePrimaryWorker:false)`创建独立工作进程，状态目录与临时数据库同属测试范围，连接使用租约指定端口。默认使用52050的其它测试入口在独占测试环境执行。

活跃房间的成员登记、准备快照和离房广播均按当前成员资格执行，共享Boss状态按房间与战斗周期维护。Boss账本边界归[本主题对应章节](关卡与房间.md#kb-06-003-1)，客户端字段归[本主题对应章节](关卡与房间.md#kb-08-023-1)，验证层级归[本主题对应章节](关卡与房间.md#kb-09-021-3)。

```text
CF09 传输
-> 房主／房间创建
-> CF70/CF71 成员名单和 CF7E 准备／队伍快照
-> CFEB/CFEC 房间资料
-> CFD3/CFD4 and CFD5/CFD6 同伴连接元组
-> CFEC 关卡资料与预加载
-> 每个客户端 CF7F
-> 全员加载确认到齐后，各发送一次 CF80/8
-> 实时转发
-> 战斗与结算
-> 离开／断线／村庄恢复
```

一个成功的前期阶段并不授权后期阶段中的未经请求的分组。

## 房间阶段 C47D 和村庄重建

C47D/144 既用于村庄装备/快捷栏更改，也用于准备房间编辑。其成功的响应必须遵循当前房间标志。在村庄状态下，保留 `C47E -> C368 -> C47F -> C379 -> C3CC -> C44C`，以便重建外观和后续的 PET。在房间/准备状态下，仅发送 `C47E -> C379 -> C3CC -> C44C`：C368 调用场景销毁，清除 shared_scene+0x24，并使准备控制器的初始化标志失效；因此，C47F 也会被抑制。这不会改变 CF80/开始构建或伪造一个阶段管理者。

## 映射身份和续行

Lumineos episode100保留通信／房间身份；资源查找转换及七个战斗资源范围见[本主题对应章节](关卡与房间.md#kb-06-003-1)，客户端选择地址见[拉米涅奥斯战斗资源选择](关卡与房间.md#kb-08-035)。七个战斗资源范围与原资源包仅有六个可达入口并不矛盾；现有道路图保留第七入口路径及返回标记，扩展范围仅为村庄道路。

CF77 mode10/100 的基础选择字节依次为 `hd/episode/dungeon/difficulty`，不含RealStage。CF78并不回显该元组：完整帧 `+0x0A/+0x0B` 是 **RealStage／ShowStage**，`+0x0C` 是DWORD room id，`+0x10..+0x12` 是槽位可用状态。新入房返回stage0/show0；已授权续关返回当前真实／显示阶段，超级Boss合法stage1不能强制清零。CF09清空上轮阶段快照，CF6C新房建立本轮阶段／show0，CF8B续关保留确认后的阶段。原生与托管构造采用相同字段含义，不能用章节、副本号、成员槽位或owner/member标志代替阶段。

`Open St Data File Error_0_1` 表示SSTG内嵌的逻辑阶段0与客户端当前RealStage1不一致，不是Win32文件错误码。将非零episode写入CF78会污染RealStage，是跨关卡／单人及多人共用的入场缺陷，而非地宫2-1独有资源损坏。该错误文本本身不能唯一确定污染来源，其他来源仍需按调用链和当次wire确认。静态消费者与错误分支由[超级Boss重置和命名资源加载](关卡与房间.md#kb-08-036)维护；双连接构造回归及原客户端验收边界由[本主题对应章节](关卡与房间.md#kb-09-021-3)维护。

CF6C仍是权威完整 `hd/episode/dungeon/stage/difficulty` 元组，adapter不篡改客户端后续CF6C；CFEB提供初始/重载阶段，CF8B提供后续转换。`absolute_slot=difficulty*3+stage_index`，CF7F在身份一致前保持关闭。四村关卡16左转的CF77基础元组仍按hd0/ep15/dg1/diff2解释，但该episode不能作为CF78阶段。

CF8B模式2选择下一副本，要求资源库包含当前关卡／章节／难度的dungeon+1/stage0；CF8C及房间身份先于CFEB/CF7F更新。构造验证覆盖dg1→dg2；客户端技能授权由其本地加载与技能门控管理。

第7入口的超级 Boss mode1 使用独立的资源名称、查找映射和 CF8C 副本设置边界；mode2 使用下一副本策略。房间章节／副本 tuple 保持原身份，资源层通过限定映射解析。

## 成员名单、身份和外观

- CF09建立大厅传输；CF6C房间创建及CF70成员初始化建立实际准备房成员身份。房主最初取得实际入房名单。
- 成员入房后，已完成初始化的观察者取得一次去重的CF71／CF72更新；重复CF70保持成员身份一致。
- CF73、CF1D及断线按成员身份发布CF74，携带离场角色和当前房主，清理可见成员与待加入记录。
- 新房间和连接代次重新建立名单与加载状态；各角色使用真实场景UID。

多人运行样本使用UID21/22；这些数值是样本身份，不是通用账号ID规则。

CF71字段策略对应公开实现 `release/components/protocol/protocol_state_sync_base.inc`：

```text
+0x34 DWORD = 0 在已保留可见观察对应的元组中
+0x38 DWORD = 选中宠物
+0x3C DWORD = 资料性别 & 1（基础模型 D8）
+0x4A/+0x4C/+0x4E/+0x50 = 角色资料的有效 HP/MP
+0x52 WORD = 0 (房间阶段)
+0x56 BYTE = 房间槽位
+0x57 BYTE = 资料性别 & 1
+0x58 DWORD = 选中宠物
+0xB4 WORD = selected-stage rank in low byte (0 blank,1 B,2 A,3 S), high byte0
```

The previous fixed1/character-level mapping is retracted. CF71 case53105 sends BYTE+0xB4 with BYTE+0x56 room slot to the native badge builder, which supports only0..3. The adapter now resolves each member's persisted rank for the selected stage/difficulty; C355 credits and CF16 settlement records stay independent. The native playable route also persists a successful non-death CF87->CF88 member result before later room entry, so the rank ledger is no longer dependent on the managed-only reward path.

## 加载和转发

房间加载、个人战斗状态和共享战斗状态分开维护：

```text
房主 CFEB -> 房主及各成员 CFEC -> 各客户端加载
各成员 CF7F -> 按活动房间与加载周期登记确认
全部确认到齐 -> 向每个成员发送一次 CF80/8 -> 客户端本地倒计时
```

CFEC负责完整关卡资料；CF80负责启动本地倒计时。每个加载周期只初始化一次共享Boss、目标和分数；每位成员独立初始化受伤、技能、资源和死亡状态。成员继承本轮完整关卡、难度及阶段身份，支持房主先完成和成员先完成两种顺序。重复开始确认保持幂等，继续关卡与重新建房分别重置加载屏障。最终响应保留各成员自己的请求低位。

受伤结算先写入角色绝对生命值，再更新同房成员的受伤表现与角色资源。结算按各角色自己的请求返回，个人死亡与成功结果分别处理；等待Boss完成的个人结算在本轮最终状态到达后独立完成。客户端状态与倒计时调用链统一见[本主题对应章节](关卡与房间.md#kb-08-023-1)；验证范围见[本主题对应章节](关卡与房间.md#kb-09-021-3)。

当前适配器转发的编号大类包括移动/活动、0x03E8/0x044C 游戏玩法、成功的效果 CF9C/CF9D 角色效果、普通终端状态、BOSS 生命值/分数，以及拾取物的移除。射击室聊天尚未纳入此转发列表。

每个转发都保留源身份、房间/页面、连接生命周期、请求优先级和顺序规则。

## 阶段入口位置与适用范围

hd0/ep0/dg1/st0中，CF80后0x044C位置关系为 **report X = actor X + 53，report Y = actor Y + 5**。标记为payload+0x0A/+0x0C的字段分别为X/Y，payload+0x14为约59.4–60次／秒的客户端时钟。

1. **X、Y必须按同一客户端本地模式配对。** CFDA与CF71的模式相关常量见[本主题对应章节](关卡与房间.md#kb-08-023-1)。X范围130–172来自房间端点77/119加53，但不能据此单独判定位置有效：
   - 模式字节=0：`(X,Y)=(130,156)`，即房间点`(77,151)`加`(53,5)`。
   - 模式字节非零：`(X,Y)=(172,115)`，即房间点`(119,110)`加`(53,5)`。
   - 样本中的`(172,115)`符合该配对；统一要求Y≈156会误判非零模式。`X<0`或`X>=300`不符合阶段入口判据，300为CF84终点。

3. **冻结位置不通过入口判据。** 一个样本连续39次报告`X=-247`。`0x044C`仅在关卡中发出，因此不能用准备房间到关卡的“ΔX”比较校准。

上述(+53,+5)与模式配对适用于hd0/ep0/dg1/st0。偏移保留原有payload相对标记，使用时按完整结构确认包头口径；其他阶段按各自位置契约处理。
