## VIP经验卡的主动使用与持久化

翻番卡经主动使用形成有效权益。卡片账本为`CharacterCards`；C3ED的VIP元组由当前在线账户与角色的会话共同授权。一般10、自由20、黄金30分别表示三种钥匙选择。适配器扣费策略为：一般／黄金各扣一把，自由钥匙以合法且有效的到期时间授权；扣卡、扣钥匙及建立`CharacterExperienceCards(CharacterId,CardCode,Expires)`在同一SQLite事务提交。

同一张仍有效卡的重复请求只确认原权益，不二次扣卡或延时。数据库入口默认不允许更换，客户端6201已有结束旧卡、使用新卡的确认流程，协议入口明确允许新卡替换旧权益，但不叠加；失败恢复原权益和库存。数量归零删除卡片行，角色之间独立，数据库重开保留数量和到期状态；原客户端重新登录后的画面验收仍归[卡片整页组合、主动使用与发布范围](兑换.md#kb-09-004-1)。

商城可购买标记保持原目录契约，300%行仍不可购买。随机奖励幸运卡不属于经验权益入口；通用拒绝回0，不能冒充容量不足。C3EE后由客户端自行请求C3E7/50及C3E9，不补发跨控制器库存包。VIP列表分类字节为0，按VIP卡号映射数量及新增提示，不与同为category3的SP／活动卡混槽。

到期字段采用原生按小时编码，适配器把“使用时刻＋目录小时数”向上对齐到可表示整点，覆盖完整目录时长；判定与列表公布采用同一边界。倍率及结算规则归[业务／地宫／计分与结算](../地宫/计分与结算.md)，协议字段和钥匙链归[VIP卡主动使用与经验权益字段](兑换.md#kb-08-003)，发布及验证范围归[卡片整页组合、主动使用与发布范围](兑换.md#kb-09-004-1)。

## 幸运卡开奖与奖励事务

幸运卡使用独立于type40经验权益的开奖分支，启用A～H八个奖池及`Sddakg._D35`对应的非零奖励记录。适配器将奖品值解释为严格递增到10000的累计区间，均匀抽取0..9999；I/J保留目录占位。验证覆盖八池全部非零奖品的加载与逐项派发。开放边界固定为实际载入且奖品区间完整的A～H（22000011～22000018）；I/J（22000019/22000020）不进入卡册可用数量、开奖或合成／开启请求。已有未开放卡库存不删除，但向客户端投影时隐藏，适配器对相应请求返回安全失败，避免进入客户端无奖池分支导致卡片页失效。

`OpenLuckyCardAsync`验证账户、角色、在线会话、持卡和神秘钥匙；选奖、扣一张卡、扣一把神秘钥匙、入库及`LuckyCardUseReceipts`凭据共享立即写事务。真正容量不足回100，保存`LuckyCardPendingDraws`但不扣卡／钥匙，腾格或数据库重开后仍发同一奖励；奖池版本或ticket/产物对应关系改变则拒绝并保留待审记录，不重抽。其它拒绝回0，成功900；不能再把不支持的请求直接回100造成6018容量误提示。

## 活动卡独立兑换与显式配置

活动卡兑换只接`C3FD/C3FE`，不复用`C3ED/type20`整页合成。每页十种卡各需至少一张，成功各扣一张；会话授权、所选单件／套装／Hans奖励提交、实例重排和`EventCardUseReceipts`在同一立即写事务完成。容量不足保存`EventCardPendingDraws`且不扣整套卡；更改该页奖池版本不能重抽旧待领奖励，已提交凭据在配置停用后仍可回原结果。请求关联窗口与幸运卡分开，限制相同。同族宠物按[宠物所有权](../宠物/所有权.md#kb-03-004-2)合并到一行：期限变体相加，永久变体本次将到期值写为0；保留旧代码时的后续永久判定仍受该节实现边界限制，抽到已永久持有的成品宠物才执行扣卡但不新增宠物、清除待领取记录的重复奖励结算，并回固定"已拥有该奖励"。三种奖项的完整字段约束及示例见[活动卡奖池配置](兑换.md)。

活动卡兑换采用显式奖池配置：从实际数据库目录读取`event-card-rewards.json`，配置有效且页面已启用时进入兑换事务；其余情况返回安全失败并保留卡片。配置为Version1、页1..10，奖项允许单件商品、Bundle整套商品或Hans金币三种形态；Quantity1仅适用于单件及Hans形态，Bundle不带Quantity。Weight为正整数，每页合计10000；完整字段限制以[活动卡奖池配置](兑换.md)为准。产物采用普通商品分支，C3FE的domain13与200各自保留原控制语义；自动化验证使用隔离奖池，仓库默认奖池须单独安装。

`EDdakgi._D19`的页1～4（50000001..40）描述秘密关卡勇士系列，页5（41..50）描述特制套装／钻石，页6（51..60）描述仿福娃宠物／套装／道具，页7～10为占位。现有活动卡开放掉落、拾取与卡册展示，集齐后由客户端启用领取按钮；兑换奖品编号、数量和概率以显式配置为准。响应使用受限固定提示；字符串安全边界、控制条件与刷新归[活动卡套卡门控与专用兑换响应](兑换.md#kb-08-006)，配置兑换验证归[卡片整页组合、主动使用与发布范围](兑换.md#kb-09-004-1)。

## VIP卡主动使用与经验权益字段

范围为World连接卡片页／合成控制器的VIP元组，不覆盖普通type10合成或type30 SP卡。点击链`0x855CA0 → 0x85AF50 → 0x41D4C1 → 0x859710`经`0x413BBF → 0x7BEC40`构造C3ED/28，调用`0xADA3E0`发送：WORD+8=40，DWORD+10=钥匙选择，WORD+14=0，DWORD+16=卡号，DWORD+20/+24=0。C3EA经`0x859840 → 0x85AAA0`写key对象+12，之后由`0x85AF50/0x85BA10`取用：10一般、20自由、30黄金、40神秘；不是暂停／续时／停止动作。`0x85AAA0`读取C3EA的BYTE+9一般数量、+10黄金、+11神秘及DWORD+12/+16自由钥匙到期／当前时间；自由钥匙有效时初始默认key状态1对应请求20。文本6201存在结束旧翻番卡并使用新卡的确认，不能一概拒绝换档；事务策略归[VIP经验卡的主动使用与持久化](兑换.md#kb-03-003)。

父分派器`0x85A270`的case50158经`0x41E6AA → 0x8599D0`消费C3EE。VIP answer800读取DWORD+8结果、WORD+16额外百分比、DWORD+20按小时编码的到期值，再经`0x416AEA → 0x866360 → 0x4013D4 → 0x8821A0 → 0x41C0E4 → 0x8829C0`更新VIP信息，并请求C3E9；最低安全总长24。普通answer400的DWORD+12产物语义不能套到800。

完成后的`0x416171 → 0x866520`请求C3E7/12：WORD+8=50、BYTE+10=0、BYTE+11=页。`0x863790`消费C3E8/140并经`0x4110F9 → 0x881BD0`处理VIP页：BYTE+11为页，BYTE+12..21为十格数量，BYTE+32..41为新增标记；DWORD+72为到期、DWORD+76为当前时间，WORD+138为额外百分比。到期不大于当前时间时清掉百分比。`0x411694 → 0x882E30`按`(额外百分比+100)`显示倍率，并将DWORD到期拆为年／月／日／小时；最高读取字节139。

VIP使用链的静态校验覆盖13个函数、2274条指令及9143字节。权益事务归[VIP经验卡的主动使用与持久化](兑换.md#kb-03-003)，计分与取整归[业务／地宫／计分与结算](../地宫/计分与结算.md)，发布及验证范围归[卡片整页组合、主动使用与发布范围](兑换.md#kb-09-004-1)。

## 幸运卡主动开奖及容量误提示

World卡片控制器点击链`0x855CA0 → 0x85BA10 → 0x851010 → 0x8512C0 → 0x7BEC40`构造C3ED/28：WORD+8=40，WORD+10=40神秘钥匙，DWORD+12=0，DWORD+16=幸运卡号。`0x8512C0`在约5秒开启动画等待后发送，该调用点没有初始化DWORD+20/+24，解析不得要求尾部为0；此例外不能推广到翻番卡的明确零尾部。

## 活动卡套卡门控与专用兑换响应

World连接活动卡控制器的C3E8/mode20由`0x863790`分派，`0x8627F0`读取十个数量槽，十种全部非零才启用领取按钮。`0x861180`动画更新经`0x40D9A4 → 0x867EA0`构造C3FD/12，DWORD+8为当前1起始页号，调用`0xADA3E0`发送；`v17==9`是动画计数条件，不是只需九种卡。C3ED/type20属于另一种整页兑换元组，不得挪用。

# 活动卡奖池配置

适配器通过专用C3FD/C3FE按显式奖池配置兑换。每个启用页定义带权重的单物品、物品组合或Hans奖励。配置决定兑换是否开放；掉落、收集与卡册展示独立运行。可选已审核奖池通过独立管理操作安装。

## 配置

UTF-8文件`event-card-rewards.json`位于活动`game.db`旁，通常在`adapter_data`。每次新兑换读取该文件。禁用兑换的配置为：

```json
{
  "Version": 1,
  "Pages": []
}
```

根对象仅含`Version`（整数**1**）与`Pages`数组。每页仅含`Page`与`Rewards`：Page为1至10中的唯一整数，Rewards为非空数组。每个奖励必须严格采用下列一组字段；字段名区分大小写，未知或重复字段均拒绝。

| 奖励形式 | 精确字段 | 约束与效果 |
|---|---|---|
| 单物品 | `Code`, `Quantity`, `Weight` | Code是现有商城物品，不是卡片目录条目；Quantity必须为1，发放该物品。 |
| 物品组合 | `Bundle`, `Weight` | Bundle包含1..20个不同的合法物品代码，在同一事务各发1件；不得同时使用Code、Quantity或Hans。 |
| Hans变体 | `Code`, `Quantity`, `Weight`, `Hans` | Code仍须是合法目录物品，Quantity为1；Hans为0..1000000整数，正数直接发放对应Hans替代物品，零沿用普通单物品行为。 |

合法物品包括衣物、宠物、宠物材料、家具与普通道具，目录禁止购买的物品也可作为奖励。同一页内所有奖励项及Bundle成员的代码须唯一，Hans项的校验Code同样参与去重。每个Weight为1..10000整数，一页权重之和必须为**10000**。权重定义适配器奖品概率。

以下完整配置使用随仓库奖池中的目录代码，演示三种形式：

```json
{
  "Version": 1,
  "Pages": [
    {
      "Page": 1,
      "Rewards": [
        { "Code": 15009238, "Quantity": 1, "Weight": 1000 },
        { "Bundle": [14002488, 14002489], "Weight": 7000 },
        { "Code": 46000008, "Quantity": 1, "Weight": 2000, "Hans": 200 }
      ]
    }
  ]
}
```

Hans项以Code作为目录校验身份，实际发放200 Hans。衣物奖励按角色性别解析；限时衣物延长已存期限。

文件大小上限64 KiB。严格解析检查必需字段、重复键、物品资格与页号唯一性。配置无效或缺失时返回受限失败并保留全部卡片。奖励使用普通物品响应分支；原子替换配置保证每次兑换读取一份完整配置。

第P页消费从`50000001 + (P - 1) * 10`开始的十种卡各一张。页1～4为秘密关卡战士系列，页5为特殊服装／钻石，页6为吉祥物宠物／服装／道具，页7～10保留占位。实际奖品由显式配置决定。

## 事务与重试

- 请求由当前账号／角色会话授权。十张卡消费、所选物品／组合／Hans发放、快捷栏／家具实例重映射及回执在同一事务提交，组合中所有成员一起原子发放。
- 容量不足时在EventCardPendingDraws保留所选奖品，十张卡全部保留。腾出空间后仍发同一奖品，每次重试沿用保存的选择。
- 宠物奖励按生物家族合并，15/30/90/180天及等级变体共享一行所有权记录。限时变体叠加目录天数，永久变体本次将到期值设为0，既有行仍保留原`ItemCode`；后续永久判定的实现边界见[宠物所有权](../宠物/所有权.md#kb-03-004-2)；阶段、等级、经验、耐久与宝石槽保持。有效宠物参与持有、容量与客户端库存；已到期宠物再次获奖从该次重新起算。重复永久宠物开奖提交扣卡、保留已有宠物、清除待开奖记录，并返回固定已拥有提示完成兑换。商城购买及待领取物品采用相同合并策略，已永久持有同族的购买提交价款并保留原宠物。材料按数量堆叠并占容量。详细所有权与事务规则由知识库[宠物所有权](../宠物/所有权.md)和[物品实例](../库存/物品实例.md)维护。
- 带待开奖记录的奖池分发变更需要管理审核。

- 响应向玩家客户端发送固定GBK提示（客户端编码），最多23个编码字节并显式追加NUL。拒绝控制字符、百分号及GBK无法编码字符；超长提示按字节预算截断，不使整个响应失败。
