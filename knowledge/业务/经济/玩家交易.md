### 玩家直接交易：C4AF..C4C1

玩家直接交易房间（C4AF..C4C1）与卡片交易所（C5B0..C5B6）使用独立协议。以下握手清单中`操作码/长度`的长度均为载荷字节数，不包含8字节帧头；随后注明的帧偏移以完整帧为基准。完整帧长度等于载荷长度加8。直接交易的格式与方向如下：

- 建房握手为 `C4AF/4 -> C4B0/20`、`C4B1/20 -> C4B1/20`、`C4B3/8 -> C4B4/4`、`C4B5/4 -> C4B7/8 -> C4B6/4`，双方随后各收一个 `C4B9/56` 对端资料。
- `C4B4` 的 payload 为4字节（WORD结果 + WORD房间号）。

- `C4BA/24` 的 payload 从帧 `+8` 开始：DWORD操作值、WORD对端scene UID、BYTE标志、BYTE交易槽位、四字节卡片元组 `(chapter,page,index,count)`、DWORD卡片代码、QWORD Hans。
- 操作值 `10` 放置／替换卡片，`20` 移除卡片槽，`30` 放置Hans。

- `C4BB/12` 定向确认 `C4BA` 请求方，payload 为 `WORD success + BYTE hansChanged + BYTE slot + card tuple + DWORD code`。对端完整卡片／Hans快照在准备阶段通过 `C4BD/48` 传送。

- `C4BC/0` 冻结本方报价，未准备的对端仍可放置／移除卡片与修改Hans；保存本方ready并向对端发送 `C4BD/48`（五个8字节卡片槽记录加QWORD Hans）。双方使用 `C4BF/0` 转发确认，最终各收 `C4C0/4`，成功结果为 `10`。

- 托管适配器的请求链为 `HandleNativeFrameAsync` 的 `0xC4BA` → `TryApplyTradeOfferAsync`（解析 `+0/+4/+7/+8/+12/+16`，校验目录及库存，更新 `TradeRoom.Offers`）→ `BuildTradeOfferResultPayload` → `BuildNativeFrame`；ready链为 `0xC4BC` → `TryReadyTrade` → 对端 `PendingNativeBroadcast(0xC4BD)`。
- 响应归属分别绑定请求方与对端。

当前验证覆盖操作值、长度、方向、字段布局及适配器字节构造；客户端显示与交互按直接交易场景独立验收。

### 玩家直接交易：C4AF..C4C1

双方ready后才能发送final；重复ready不撤销已记录final，重复final不重复转发或支付。五槽中同卡的数量按总和校验，结算事务再次核验实际库存、金币、接收容量和双方活动会话。DB异常返回双方C4C0/result70并解除settling，卡片与金币整体回滚。

- `C4BE/0` 取消当前报价轮，不离开交易房：清空双方Offers（卡片及Hans）、ReadySessionIds、FinalSessionIds，并向本人及对端各送一个C4BE。
- 客户端兼容配方将取消处理扩展为双边报价重置，双端清空后重新报价。
- 客户端地址与作用域由[玩家直接交易的托管请求分派链](#kb-08-071)维护，精确修改与恢复由`knowledge/指南/客户端二进制补丁.md`维护。
- 取消后的空报价开启新一轮，上一轮卡片和金币不进入新一轮。
- 报价轮OfferEpoch在取消及成功结算后递增；跨取消轮的异步库存读取请求拒绝，避免旧请求重建隐藏报价。

断线、离场与C4C1关闭属于[玩家直接交易房间路由](#kb-05-025)维护的房间生命周期，不与取消报价混用。当前发布契约由适配器事务、客户端兼容配置和运行包清单共同维护。

### 玩家直接交易房间路由

- 直接交易的卡片／Hans字段、C4BA操作值、C4BB/C4BD方向和结算结果见[玩家交易协议](#kb-03-044-1)。
- 房间生命周期和多人路由边界如下：C4AF 邀请必须来自同一可见场景，C4B3 创建后仅邀请方先加入，C4B7 由被邀请方加入；两方均加入后才允许 C4B8 对端资料、C4BA offer、C4BC ready 和 C4BF final。
- 断线、离开场景或跨场景时撤销TradeRoom，普通城镇同步使用独立的场景状态。
- C4BE取消当前报价轮并保留双方房间成员，双边清理与重新报价规则见[玩家直接交易：C4AF..C4C1](#kb-03-044-7)；C4C1继续承担离场生命周期。

### 玩家直接交易的托管请求分派链

当前发布源码的托管请求分派链为：

```text

HandleNativeFrameAsync case 0xC4BA
  -> TryApplyTradeOfferAsync
  -> payload +0/+4/+7/+8/+12/+16 解析
  -> CardCatalog + GetCharacterCardsAsync + TradeRoom.Offers
  -> BuildTradeOfferResultPayload(12)
  -> BuildNativeFrame(0xC4BB)


HandleNativeFrameAsync case 0xC4BC
  -> TryReadyTrade
  -> TradeRoom.ReadySessionIds
  -> PendingNativeBroadcast(0xC4BD, 48) to peer only


HandleNativeFrameAsync case 0xC4BF
  -> TryRequestTradeSettlement
  -> CompletePlayerTradeAsync
  -> BuildNativeFrame/PendingNativeBroadcast(0xC4C0, 4)

```

`C4BA` 操作值为 `10=put/replace card`、`20=remove card`、`30=put Hans`。`C4B4` 最小完整帧12字节（payload4），`C4BB` 完整帧20字节，`C4BD` 完整帧56字节；本节维护适配器解析、构造与定向响应契约。

- 客户端直接交易dispatcher为`0x7996F0`。
- C4BA发送`0x793D90`从控制器+0x1F8取对端UID、+0x1F0取槽位、+0x228取QWORD Hans。
- C4BB在`0x79AE93`进入，读帧WORD+8、BYTE+0x0A/+0x0B、BYTE+0x0F、DWORD+0x10；C4BD在`0x79A9B6`进入，五行从帧+8起、步长8，Hans读DWORD+0x30/+0x34，最小完整帧56字节。

- `0x799F88`的C4BE取消处理经精确兼容替换扩展至`0x799F9C..0x79A06D`（209字节）：保留寄存器／flags，清理并置零控制器+0x460起十个连续槽指针（本方五个、对端五个），清+0x1EE对端ready、+0x570等待应答、+0x4B4本方SP报价标志；调用`0x7922E0`／`0x792330`将本方+0x228和对端+0x230的QWORD金币输入归零，调用`0x791540(0)`恢复本方准备按钮与输入；指示器+0x49C经`0x7A2510`把双方状态设为1；`0xADA730`消费一次C4BE。
- 末尾返回`0x79A06D` dispatcher出口，交易房成员保持不变。
- 完整原值及新值由统一兼容配方生成。

上述地址、字段和长度构成当前客户端兼容约定；二进制修改、安装、校验与恢复步骤统一见《客户端二进制补丁》。

### 玩家直接交易验证与安装范围

- 当前直接交易遵循[交易事务规则](#kb-03-044-7)的单边ready冻结、未准备方继续报价、双确认、原子结算、取消双边清空与同房重开约定。
- C4BB只回复报价请求方，C4BD只向对端发布准备快照；209字节取消修正纳入内嵌兼容配方的`dungeon-state`组，启动器通过兼容工具应用并从更新后的game.exe派生客户端副本。
