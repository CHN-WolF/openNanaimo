# DIY／任务／接入策略

## 当前能力

| 层 | 可复用内容 | 适用边界 |
|---|---|---|
| 普通任务 | 既有 QH/QT、十个普通槽位、评估和交付事务 | 目标判定采用已实现类型 |
| 勋章主线 | 71系列、type1固定槽位、末章兑奖和领取账本 | 71系列独立定义 |
| 章节数据 | 独立73系列16章目录、逐目标和逐动作映射、待审中文与立绘候选 | 离线审核与隔离候选；活动任务目录独立维护 |
| 章节宿主候选 | 独立存档、场景／战斗代次、逐页确认、原状态保留迁移及整包领奖事务 | 隔离主机构造；生产接入按真实确认协议和奖励审核契约审批 |
| 修道僧 | 四个独立挑战、中文对白、胜败分支、成功收据 | ClearMask定义独立挑战进度 |
| 跨村候选 | C365前置授权复用ClearMask | 首次授予与章节前置另行定义 |

跨村候选的唯一策略入口为[修道僧跨村授权](../../角色/新手引导/跨村前置.md#修道僧跨村授权)。它是独立可启用的玩法，挑战进度和章节完成状态各自维护。

## 第一章闭环

章节实现的完整契约为「活动type2任务 → 正确场景进场对白 → 可信地宫结算 → 正确场景离场对白 → 单次领奖与下一章」闭环。CN与KR分发器及字段布局分别定义；通用章节接入需要客户端执行器和确认链共同配套。

渲染层优先复用[NPC输入与对白](../NPC/输入与对白.md)和[立绘生命周期](../NPC/立绘与动画.md)。通用脚本次序、场景触发、当前目标授权和确认事务使用独立状态空间、事件入口和文本缓冲区，与既有窗口绘制及四挑战协作。

## 进度与事务设计约束

章节存档的设计契约如下：

- type1与type2各有固定槽位；章节不得进入现有 `ComputeMainLine` 的非出售任务选择集合。
- 当前目标索引始终在定义范围内，完成后保留合法末项；累计数不能替代索引。
- 角色、在线会话、当前地图和战斗代次共同限定确认资格。错误页面、未开始任务、取消、重复确认和旧战斗不得推进目标。
- 战斗目标只能从已提交的可信结算推进；type40的具体通关集合和难度属于待确定的启用条件。
- 逐目标进度、领取账本与奖励整包提交；容量不足、物品不兼容或余额越界时全部回滚。重复请求不得重复奖励或跨过多个目标。
- 旧普通卷轴、12勋章、师徒链尾、哈希奥哨兵与欠发恢复保持原行为；不自动将旧独立挑战折算为整章完成。
- 第16章后继为0；不得利用其他资源占位补写不存在的官方第17章。

## 候选实现

`ChapterStoryPolicy`、`ChapterStorySession`和`DatabaseService.ChapterStory`实现隔离候选。显式首次开始从Episode1起步，要求账号／角色在线会话匹配且教程完成，不从勋章链尾自动接入；已存在候选进度不回填、不重置。旧候选表只有精确匹配的Episode5起点约束会在事务中扩展至Episode1，未知字段、触发器或索引拒绝迁移，避免丢失扩展数据。

候选type40采用“本章进场对白后，三个不同普通地宫、任一难度”的项目构造策略，按项目策略登记。逐页票据绑定任务、修订号和场景代次，每次确认重新核对账号／角色会话；取消、重进同场景、页序错误和旧票据均不推进。结算票据另绑定战斗代次、episode和dungeon，并要求可信结算对象。当前交付API的作用域为主机构造，生产调用者按确认协议核验事件来源。

Episode4／8／12／16仅在本章离场对白完成后读取既有ClearMask对应位，沿用唯一修道僧账本，章节对白与独立挑战各自保留完成条件。奖励未审核时停在`RewardPending`；`AfterRewardTransaction`由隔离数据库领奖事务计算下一状态，与奖励和领取账本一起提交。全16章顺序测试仍归属纯状态策略，不代表各章奖励已经获准。

`ChapterRewardPolicy`要求适配器内部审核输入精确绑定章节包SHA-256、任务ID、原始奖励顺序／三元组、目录期限和审核编号，任一未支持成员拒绝整章。当前没有生产审核提供者，测试审核记录仅供隔离测试使用。`DatabaseService.ChapterRewards`采用独立`CharacterChapterClaims`账本，以角色／任务为唯一键保存修订号、奖励摘要和审核编号；同一收据重试返回已领取，身份冲突拒绝。金币、经验、库存／卡片／宠物、快捷栏、领取记录与下一章在同一SQLite写事务内提交，容量不足、数量损坏、数值溢出或后续写入失败均回滚。经验奖励使用当前成长曲线；满级溢出整包拒绝，不静默裁剪奖励。

领奖会话票据另绑定任务修订号、离场对白场景及场景代次，取消或重新进场使旧票据失效；领取时重新校验账号／角色在线会话。票据为一次性，失败重试须重新取得票据。第16章领奖只提交完成标记，后继保持0。该API没有客户端操作码调用者，场景与事件来源的生产可信性仍须由CN接入链证明。

候选宿主`--chapter-story-reward-audit`只读查询`CardCatalog`与`ShopCatalog`，保留原始三元组、CN名字、合成结果、目录期限和缺失身份。各行授权为`grant_allowed=false`，目录命中与奖励审核分别登记；缺失列表及受测程序集由工程验收页维护。不能直接复用仅处理部分奖励类型的旧任务交付循环，否则可能漏掉时装／券或混淆宠物期限。

## 验收范围

验证分别覆盖目录重派生、冲突、本地化、状态／事务和匹配客户端。实机必须覆盖取消重播、掉线重登、结算返城、四村NPC／立绘、背包满、重复领奖及链尾终止。首次授予与旧档入口是项目政策，须在启用前明确，按项目策略登记。

构建、检查与候选启用见[操作指南](../../../指南/韩服剧情目录准备.md)，当前结果见[验收归属](../../../工程/验证状态/章节剧情与跨村门槛.md)。
