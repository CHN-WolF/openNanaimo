## 情侣关系与权益

- 求婚绑定发起者、接收者、戒指代码、非零稳定库存实例和30秒有效期；求婚列表与普通游戏道具页共享同一戒指实例身份，响应仅由对应接收会话提交。双方当前账号／角色／会话在库存与关系事务中共同校验；接受和明确拒绝均消耗所选的一枚戒指。接受时建立情侣关系并启用对应权益；拒绝时保持单身，申请方收到当前库存刷新。决定按绑定上下文单次提交，重复答复保持同一扣除结果。
- 情侣姓名、关系和戒指等级持久化。会话刷新与城镇角色构造均同时携带伴侣姓名和戒指等级，空关系清除两者；本人及旁观显示另受持久称号选项门控，C355/C36A字段与显示门控分别见[情侣资料字段](情侣.md#kb-08-012-2)与[情侣显示及邀请](情侣.md#kb-08-050)；结婚、双方分手及强制分手按[同身份角色替换](../城镇/角色实体.md#kb-02-019)规则更新，保留场景和位置，同页旁观者取得更新后的角色资料。银、金、钻戒分别增加个人HP／MP道具恢复20%、50%、100%，恢复按有效资源上限封顶，适用于城镇、托管地宫和原生地宫。
- 戒指权益统一按实际代码解析：银戒 `43000001`、金戒 `43000002`、钻戒 `43000003`；未知代码使用零权益。金戒、钻戒在情侣双方参与当前房间同阶段战斗时分别使用120%、150%的角色结算经验；组队、宠物、评级、分数和Hans沿用各自规则。
- 金戒、钻戒解锁情侣心情符号31–39。权限由有效关系和戒指确定，身份由活动角色确定。
- 金币分手券43100001的“使用”校验当前关系和所选实例并打开双方确认；伴侣同意后原子解除关系并扣除一张，拒绝或取消保持关系与库存。两类分手券均使用1..84的游戏道具身份。强制分手券43100002的“使用”建立30秒确认上下文；确认提交时按当前关系、账号／角色／会话及原库存实例执行单次扣券和双向关系更新。取消保留关系与库存，重复使用沿用原确认期限，变更库存或关系后的旧确认失效。
- 求婚资料分别投影人物等级和地宫称号，称号按有效地宫等级索引显示。
- 准备阶段保持房间身份初始化；队员先接收含遭遇开关的CFEC地图预载，不在地图数据前推送CF80。队员自己的CF7F加载确认或已授权的最终CF80均使用当前战斗开始边界；最终CF80之前按当前阶段发布一次C588伴侣身份；托管身份统一使用场景 UID。特殊遭遇在地图准备时按同房有效情侣关系开启，全房成员取得一致的场景状态；战斗开始后按实际参战名单及完整关卡选择校验。情侣经验仍归属于双方有效参战角色。
- 情侣个人HP／MP道具的共享覆盖城镇、准备房、地宫战斗及结算等待：城镇要求当前已认证队伍中的双方在线；房间要求当前成员归属，原生房间另核对worker端口／代次及已有关卡选择，名单早于房主选图时以双方合法准备名单为界。双方存活、关系有效时，C43D／C46D背包食物在同一SQLite事务中只扣使用者一个稳定实例，并写入双方资源；伴侣账号／角色／会话、关系及戒指在事务内复核，失败整体回滚。双方并发用药按会话ID排序锁定资源合并，不把伙伴恢复覆盖为旧快照。普通队友只观察资源，不获得个人药效。双方各自按选中宠物及装备后的有效上限封顶，不回写基础MaxHp/MaxMp，也不因满血一方的零实际增量取消另一方恢复。
- 城镇使用者保留C43E→C43F实际恢复增量，C46D使用C46E→C430→D8FF绝对资源；伴侣接收自身D8FF。准备房使用请求驱动的F100→F108→CF72/116同步现有角色。地宫战斗及结算期的背包食物使用完整CF94/24，双方槽位均为0xFFFF，HP／MP字段为各自已提交实际增量，尾部四字节清零；C43F保留零增量库存完成，不重复增加MyInfo。战斗／结算不发送D8FF或CF72作为用药更新，避免被丢弃或清除快捷栏保护数组。原生CF93快捷栏保留worker既有双方CF94广播，使用者真实槽位、伴侣0xFFFF，不在managed层再加一次恢复。具体消费链与否定边界归[求婚专用库存与戒指实例](情侣.md#kb-08-011)。
- 结算用药保留SettlementFrozen及结算／离场凭据，只更新绝对资源和worker状态，不解锁旧战斗；授权续关、回城、退出及加载切换期间拒绝背包恢复，死亡／观战伙伴不被药品复活。三档戒指恢复倍率、双方资源保存和连续关卡资源状态共同维护。恢复先完成持久化再发布会话资源，失败保留重试资格。原生状态读取使用独立二进制临时流，读取失败中止操作并保留库存；每次原生快捷栏用药在扣除前重新绑定当前连接代次。同身份重连与跨关使用当前有效绑定；成员名单早于房主选图时，按已认证队伍房主及worker代次补齐关卡身份，使普通／超级地宫共享资格判定。托管房间以当前CharacterRecord维护资源，背包读取不采用旧城镇快照。

情侣验证覆盖地图开关、身份顺序、共享恢复及双方持久化；特殊怪物的资源属性与运行实例血量规则归属[业务／地宫／索引](../地宫/索引.md)，双端显示按实际地图独立验收。

## 情侣结算经验

金戒、钻戒在双方处于同房同阶段时，分别将结算计分基数按120%、150%计算，增加额进入奖励分数；总分最后按25%转为人物经验。托管地宫绑定实际战斗参与者，原生地宫绑定共享房间、完整关卡选择及本角色结算行；同一结果只进行一次倍率处理，奖励分数、总分和持久化经验使用同一结果。评级、宠物经验、Hans和卡牌继续由各自规则决定。

### 求婚专用库存与戒指实例

强制分手的使用入口 `0x7F49F0` 与确认窗口 `0x81D440` 分离；`0x8BF600` 在用户确认后提交关系变更。适配器使用阶段只建立有期限的库存／关系快照，确认阶段原子校验并提交。求婚图标经 `0x53F440/0x53F590 -> 0x8BE280 -> 0x8BF060` 按 `1243 + 地宫等级` 选择资源；请求投影payload `+22/+23` 分别保存人物等级／地宫称号，求婚响应对应payload `+24/+25`。

`0x008C0730` (`sub_8C0730`) 消费情侣专用库存页：完整帧 `+0x0A` 为行数，行从 `+0x0C` 开始，代码位于 `+0x0C`、实例身份位于 `+0x10`；只接收 domain43 代码，并按代码后缀写入银／金／钻戒的数量和实例身份表。`0x008BF170` (`sub_8BF170`) 在求婚页按当前戒指槽的数量门控确认按钮，构造请求时同时写入选中的戒指代码和稳定实例身份，确认流程因此依赖专用库存与普通游戏道具页的一致实例映射。

当前适配器以1..84范围内的稳定会话身份实现这条调用链；C430、C46A、快捷栏和求婚事务按同一游戏道具实例投影换算，数据库紧凑序号只用于持久层定位。

### 情侣地宫身份及特殊遭遇状态

伴侣地宫身份经 `0x6EBD28 → 0x4029E1 → 0x709060` 写入管理器WORD `+0x1032`。房间资料完整帧 `+0x325` 经 `0x6F62F0 → 0x415361 → 0x708C80` 写入管理器BYTE `+15`。情侣场景使用 `CFEC/808 +0x325=1`，C588/12先于最终CF80/8发布。场景调度器 `0x6A07D0 → 0x41451F → 0x6C9D90` 识别子资源标志2的情侣怪物，经 `0x414C90 → 0x6A3F20` 读取开关。地图准备按有效同房情侣关系设置全房共享遭遇状态，人物伴侣身份独立发布。

用药结果 `CF94` 完整长度24字节：角色UID位于 `+8`、槽位WORD位于 `+0x0A`、道具代码位于 `+0x0C`、HP／MP恢复WORD位于 `+0x10/+0x12`，尾部两个WORD完整初始化。尾部四字节初始化为零；原生快捷栏用药使用真实槽位，伴侣使用0xFFFF；背包用药的双方槽位均为0xFFFF。HP／MP字段分别携带各角色经自身有效上限裁剪后的实际恢复增量，不保证双方数值相同。托管构造的payload必须为16字节，不能保留旧12字节截断。`0x6F1D9F` 按角色身份路由；`0x6F1F82..0x6F1FB0` 仅对槽位0–5执行快捷栏消耗，伴侣恢复使用 `0xFFFF`。恢复状态以角色、战斗周期及单次结果身份去重，并同步有效HP／MP上限与持久状态。当前内部角色状态采用schema4、payload5704／完整帧5712，payload DWORD `+5120` 保存伴侣UID；其后还有版本、曲线、64位人物累计经验和扩展卡片区，精确布局归[内部布局](../../基础/桥接布局.md)。伴侣资格在当前活动房间重新绑定。历史5120→5124字节补零机制不是当前迁移处方：已验证的schema3／5144字节／CurveVersion3恢复快照按[战斗卡片入库与独立扩展区](../卡片/卡册.md#kb-03-028)的规则归档原字节，并从主卡片表重建扩展区；未知长度／版本拒绝，旧待提交journal不得隐式升级，须先用匹配旧程序恢复。

### 情侣资料及表情权限

C355消费链为 `0x00531DA3 -> 0x0041646E -> 0x00530C90`；情侣姓名从包`+0xDF`传至原生`0xA76170`，按是否非空写入`manager+0x4F6C`。戒指`WORD+0xF0 -> 0x4DDA30 -> manager+0x1028`独立于该布尔标志。

C355 进度填充止于完整帧 `+0xDE`；`+0xDF..+0xEF` 保持17字节情侣姓名，`WORD+0xF0` 保持戒指后缀。空情侣关系写入空姓名与零戒指，原生 `0xA76170` 将 `manager+0x4F6C` 置为 false，在翻页戒指资源查找前关闭门控。

隔离 original-x86 对照执行原生姓名／戒指 setter 和下一页 gate，CRT bounded-copy、strlen、memset 为模型，缺失记录 lookup 按 NULL 建模。越界姓名构造有一次lookup／predicate调用并在上述地址无效读；空姓名Network及两种Stand_Alone构造均为零次lookup／predicate、`closed-before-page2`。这是有假设的隔离执行，不是全客户端 UI 验收；构造输出也不是实时 wire。

## 情侣标识与场景更新

姓名、戒指与字符串构造见上文“城镇称号与角色等级”。绘制另有独立门控，构造与显示分别满足各自条件：

- C36A/112的`WORD+0x6E`是被观察角色的显示模式，`0x53E0C0 -> 0x535530 -> 0x4FA9F0`在`0x4FAA95`写入actor`+0x32F8`。该字段独立于UID；场景身份仍由控制值位20..31提供。显示模式按角色选项投影。

- `0x4FE970`绘制actor：`+0x1EC != 0`为本人，读取`[0xD869D8]+0xC0`的option[0]；其他人读取actor`+0x32F8`。模式0隐藏；模式1走其他称号；模式2且伴侣名非空才绘制情侣文字和戒指。名称actor`+0x31D4`、格式化文字`+0x31EC`、图标对象`+0x31D0`、戒指`+0x32F0`是独立字段。

- C355/728的`WORD+0x2D4/+0x2D6`在`0x531125..0x53113F -> 0x410F3C -> 0xA86120`恢复显示模式及六个选项位；模式没有初始化为2时，补发伴侣姓名不能开启本人的绘制。旧档缺少设置行采用默认2/0；显式设置0/1必须保留。

- 选项保存构造`0x8AB0D0`为C5BC/12；`0x8A877B..0x8A8799`在完整帧+8写mode、+10写六位flags并发送。适配器以活动账号/角色/会话原子保存`CharacterTownOptions`，只接受payload4、mode0..2、flags0..63；不伪造C5BD或额外C355/C368。本人UI直接应用设置，他人按后续正常角色快照读取。

- C584/C586经`0x536440`局部更新关系，C355经`0x530C90`进入页面初始化；关系变更使用前者，保留双方原场景和坐标。旁观者按同页可见性获得对应角色的最新关系、坐标与外观。

情侣文字绘制要求本人option[0]及他人mode使用有效显示模式，并同时具备伴侣姓名和戒指。当前修正统一C355选项恢复、C36A被观察角色模式和C5BC持久化；对应构造及发布约定已验证，画面按双端场景验收。

## 情侣与场景同步

- 金币分手券进入双方确认流程，伴侣同意后单次扣券并解除关系；拒绝与取消保留当前状态。
- 同房同阶段存活的情侣共享个人HP／MP药品恢复，银、金、钻戒分别增加20%、50%、100%恢复量，双方按各自有效上限封顶，用药者承担单次库存消耗。
- 特殊怪物按资源分别维护生命、类型、碰撞攻击、得分与防御，运行实例使用统一的难度缩放规则。
- 城镇角色按身份替换更新情侣状态；进场同时发布角色、宠物和静止坐标，重复查询保持单一角色实例。
- 多人普通续关与超级Boss加载保留每位成员的有效预载状态，资料刷新与快慢成员加载保持独立；退出清理与城镇入口分别完成。

- 房主和队员均在有效开战确认后建立当前战斗状态，情侣共享与死亡续战使用同一开始边界；重复确认保留本轮资源与扣款状态。
