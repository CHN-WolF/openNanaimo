### 组队结果页与观战结算入口

<a id="组队评分页与观战结算入口"></a>

`--dungeon-state` 将CF88完成排序的调用包装为统一结果页入口（历史文档称评分页）。原生排序先完整应用三行评分与角色状态；普通地宫模式下，活动战斗页随后切换为结果页。已经进入结果页的成员保留当前结果。键盘与鼠标的上一帧快照在结果就绪时更新，继续按钮及快捷键使用结果页上的新输入变化。两处倒计时继续采用手动确认策略。

| 站点 | 原字节／范围 | 派生行为 |
|---|---|---|
| `0x006FADE9` | `E8 E3 71 D1 FF` | `E8 92 83 FE FF`，CALL转至`0x006E3180` |
| `0x006E3180` | 96字节`CC` | 调用原`0x00411FD1`排序入口，保存寄存器及标志，处理结果入口后恢复并返回；兼容连续`CC`原区域及已登记的单控制器版本，安装双控制器编码 |

- 包装器使用`0x006658E0`取得游戏管理器，模式`BYTE+3`∈{0,1}；页面`DWORD+0x10F0`为4时经`0x006692E0(6)`置为结果页6，为6时保留已有结果。
- 输入对象由`0x0040ED77`取得，键盘当前256字节`+12`复制到上一帧`+268`（`+0x0C`→`+0x10C`），鼠标当前16字节`+528`复制到上一帧`+544`（`+0x210`→`+0x220`）。
- 包装器保留原排序的返回值、寄存器、标志及栈平衡。
- 当前96字节目标代码SHA-256为`FFA9D9AFFAC4E87B5290D1C6EB17F0060722B9150E8365FEC4968C133A7B3740`。
- 旧版仅支持模式0，旧代码SHA-256为`C1E751ECD985291E0AFDECF24315DD2F8A3D21BC54EDD86EC872BF37F4B7B37F`，仅作为已登记迁移输入，不用于核验当前目标。

完整派生、应用与回退步骤（本节为该二进制补丁的操作入口）：

1. 关闭目标客户端及使用该源文件的社交槽位，记录目标`game.exe`大小与SHA-256。按PE节表将上述VA映射为文件偏移，核对调用点与96字节代码区域的原生字节或当前目标字节；完整匹配两站点后继续派生。
2. 使用下列命令检查并生成独立候选文件。派生器生成相对CALL、模式／页面条件与输入快照复制指令，剩余代码区填充为`CC`；调用点和代码区共同作为一个兼容项更新。
3. 同步执行手动计时、回城按钮及其他已登记地宫兼容项，复核所有站点、文件长度及重复派生的一致性。
4. 检查候选通过后，以相同参数追加`--overwrite --apply`。工具将目标原文件保存至`<overlay-root>/backups/<before_sha256>/game.exe`，逐文件原子应用并校验。报告中的`verification.all_pass`应为`true`，`apply_results`登记前后摘要及备份位置；社交槽位按更新后的源身份重新派生。
5. 回退时关闭目标客户端及社交槽位，按报告中的`before_sha256`核对完整备份，将其完整恢复到原目标`game.exe`，再次核对文件大小与SHA-256；社交槽位按恢复后的源身份重新派生。备份与目标以各自完整摘要绑定。

```powershell
# 客户端与派生目录使用两个独立目录。
python -B scripts/prepare_client_compatibility.py --source-root "<client-root>" --output-root "<overlay-root>" --dungeon-state --dry-run
python -B scripts/prepare_client_compatibility.py --source-root "<client-root>" --output-root "<overlay-root>" --dungeon-state
python -B scripts/prepare_client_compatibility.py --source-root "<client-root>" --output-root "<overlay-root>" --dungeon-state --overwrite --apply
```

两站点分别接受原生或目标编码，支持完整目标重复应用及已登记状态组合；字节门禁精确匹配后才提交输出。文件长度保持一致。精确迁移与隔离执行覆盖普通地宫／其他模式、页面0／3／4／6／10、原排序调用一次、输入边界及寄存器／标志／栈保持。验证范围为字节迁移、页面分支及指令执行。

## 组队与超级BOSS结算入口

两个战斗控制分支共同等待完整结算数据，再进入结果页面。结果排序先完成，页面状态随后切换；新的确认操作从结果页建立独立输入边界。完成数据后的入口`0x006FADE9`、结果发布函数`0x006E3180`／96字节、模式与页面范围及排序输入快照与本节入口同源，统一维护在[组队结果页与观战结算入口](#df-11-002-result)；下表只保留超级BOSS双控制器分支与最终总分排序的独有内容。

| 修改点 | 当前约定 |
|---|---|
| 普通控制分支 | VA `0x0066CD71`，`74 1A`改为`EB 1A`，转入当前战斗更新的后续分支 |
| 组队控制分支 | VA `0x0066CD45`，`74 1A`改为`EB 1A`，转入当前战斗更新的后续分支 |
| 最终总分排序入口 | VA `0x00762230`，6字节评级分支改为进入总分比较区；原字节`0F 8D A1 00 00 00`，目标字节`E9 A2 00 00 00 90` |
| 最终总分比较区 | VA `0x007622D7`，原154字节按精确配方等长替换；控制器行步长`0xAC`，`+0x4BC`最终总分降序、同分`+0x448`角色UID升序，保留评级值；保持`+0x4E8`就绪门控和原生交换／绘制路径 |
| 精确配方 | `scripts/dungeon_result_compat.py`中的`encodings()`、`sorting_sites()`与迁移函数；两个新增排序位点随`--dungeon-state`派生，既有客户端及多开social派生副本均须重新应用／核验 |
