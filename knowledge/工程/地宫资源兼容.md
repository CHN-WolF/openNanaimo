## 启动一致性

兼容脚本识别成对原生场景及精确入口格点，保持它们，不再套用旧 L7 入口坐标。缺一页或触发区异常会拒绝处理。无原生场景时仍沿用既有布局。

社交副本启动前核对资源身份及内容。目录链接会读取相同内容；若系统退回独立目录复制且副本已过期，则拒绝启动，要求重建副本，确保资源版本一致。资源标记只在内容一致后更新。移除源资源包后，带旧标记的副本也会被拒绝。战斗目录另由`manifest/lumineos_combat.json`约束，不用资源标记代替代码身份校验。小地图在完整资源验证后使用B84关闭未来关卡，保留L7/L8原生前置；无资源包仍使用B80，不全局解锁。

## 3. 拉米诺斯村地宫7兼容链
拉米诺斯村地宫7入口由五个边界共同构成：C355 前置进度、村庄道路、关卡资源命名、adapter 资源映射和嵌套 PON。原客户端读取 C355 `+0x80..+0x87`，并对 `k=0..21` 的每项要求两个 bit 同时为 `1`。静态链为：C355 分派 `0x0052C100` → 状态构造 `0x00544000` → 前置字段写入 `0x0054EDD0`；移动流程 `0x005000A0` → 前置判定 `0x00509EC0`，逐项检查 `+0x48` 的 bit `2*k` 与 `2*k+1`。

### 兼容链组成

地宫7由前置进度、村庄道路、关卡资源命名、adapter资源映射和嵌套PON共同提供。`--dungeon7` 负责小地图发布边界、道路、已知补制图像撤回及资源别名派生；家具与屋外外观系统通过上面的完整命令同时应用。C355低44位前置字段由适配器在最终构造阶段统一写入，角色进入使用同一状态周期。

### 3.1 C355 前置进度

第五村使用 C355 完整帧 `+0x80..+0x87` 的独立 64 位前置字段。客户端移动判定对 `k=0..21` 的每个前置要求两个 bit 同时为 1。

完整 adapter 在所有 C355 构造完成后，仅设置低 44 bit：

```text
C355 +0x80..+0x87
FF FF FF FF FF 0F 00 00
```

实现位置：

```text
release/components/dungeon_unlock/unlock_patch.inc
```

约束：

- 只设置 22 个前置对；
- 保留 bit44..63，包括最终完成对；
- `+0xC8` 关卡显示字节沿用原生语义；
- 不主动推送 C367/C368；
- 仍由 C354 请求驱动 C355。

### 3.2 P03 村庄道路 pack

原始第五村 pack 只有前六个入口的连通道路，page17 没有通往 page18 的出口。地宫7需要 P03 道路 pack：

```text
Village_map_image/Village_map_image.pack
```

派生器读取 pack 目录与第五村 50×36 单元网格，按字段语义生成道路；不要求原始 pack 或输出 pack 命中固定哈希。

基础CN兼容布局的P03包含16条补充双向道路，并保留以下入口；这些格点不适用于韩服原生L7/L8布局：

- page18 单元格 `x22..27/y3..4` 的地宫7入口 action `166`；
- page18 `(25,6)` 的返回 marker `169`，返回像素坐标 `(400,96)`；
- 入口恢复到补制美术引入前的区域，不再迁往左侧实验室图像；
- 已有 `160..166` action；
- 未增加虚构的 `167..182` 地宫入口。

韩服原生L7/L8布局由派生器独立识别：page18的action166入口为`x8..11/y5..9`，marker169返回格点为`(10,15)`；基础CN布局对应`x22..27/y3..4`和`(25,6)`。原生布局不套用旧入口与返回坐标，也排除未实现的L9道路。判定见`scripts/prepare_client_compatibility.py`的`native_layout`分支及[L7/L8资源移植](../指南/L7-L8资源移植.md)。

P03 提供道路连通性；战斗资源覆盖范围由 SSTG、SMMO 与 PON 清单独立确认。

### 3.3 地宫7关卡 SSTG 别名

客户端请求的兼容路径为：

```text
flying/hd0_ep22_dg00_st01.sstg
```

使用者应从已有的：

```text
flying/hd0_ep22_dg01_st01.sstg
```

制作**逐字节相同**的别名文件。该复制关系由派生器执行；不对源文件或别名文件设置固定大小／哈希门禁。

只复制 SSTG 文件名；文件内部已经存在的 dg01 SMMO 引用保持不变。

### 3.4 adapter 资源查找映射

地宫7在村庄／房间身份中保留 `hd0/ep100/dg6/st1`，但资源目录使用 `ep22/dg1/st1`。完整 adapter 对**普通目标和 Boss**使用限定映射：

```text
hd0 / ep100 / dg6 / st1
    ->
hd0 / ep22 / dg1 / st1
```

该映射只用于资源查找，不改写房间身份、客户端显示 tuple、奖励归属或持久进度。

### 3.5 PON 同家族兼容别名

关卡嵌套依赖使用以下别名：

```text
源  flying/pon/mis_ep22_dg01_m_196.pon
目标 flying/pon/mis_ep22_dg01_m_196_02.pon
操作 逐字节复制，不设置固定大小／哈希门禁
```

该文件是同家族兼容别名，其外观、轨迹与参数沿用源文件。`gui_launcher/resource_patches/superboss_projectile_alias.json` 记录派生关系和适用范围；GUI 以路径与生成结果为准。

### 3.6 显示边界

小地图初始化 `0x009000D0..0x00900156` 先循环查询原生前置条件并写入各章节开关，随后 `0x0090012F` 的 `C7 80 7C 0B 00 00 00 00 00 00` 把第7关强制关闭。派生器以整个初始化函数的原始／L7／L8完整字节签名为门禁，只将该指令的偏移 `0xB7C` 改为 `0xB80`（实际唯一变化位于 `0x00900131`，`7C → 80`），使强制关闭边界移到第8关，第7关保留原生条件的查询结果。安装并完整校验L8资源包时，目标位移改为`0xB84`（同一地址字节`7C/80 → 84`），固定关闭第9关，保留第7／第8关的原生条件；保留全局解锁配置。重复应用不再变化；未知函数字节拒绝写入。

该修正仅调整小地图章节开关边界，C355前置进度、移动门槛、战斗资源、page17→18道路和action166保持各自契约。

完整应用与恢复步骤：

1. 使用 `--dungeon7` 或 `--all` 选择该兼容项。
2. 解析PE32区段，将 `0x009000D0..0x00900156` 映射到文件偏移，并对整个初始化函数匹配登记的原字节或已应用字节。
3. 在内存中仅修改 `0x00900131`：无L8资源时使用`80`（B80），已验证L8资源时使用`84`（B84），原始值为`7C`（B7C）。
4. 逐字节复核完整函数、唯一变化位置及第7／第8关开关目标，生成独立覆盖目录和兼容报告。
5. 使用 `--apply` 时先将完整 `game.exe` 按SHA-256保存到 `backups/`，再执行单文件原子替换；重复应用收敛到相同文件。
6. 回滚时关闭客户端，恢复该次报告登记的完整EXE备份并核对SHA-256；单项恢复在完整函数门禁通过后还原该次应用前的 `7C`、`80` 或 `84`，步骤见3.6.1节。

入口兼容链保持以下边界：

- 新客户端进程的首个 C355 固定发布 `map/page=0/0`，避免原生 `FirstVillageFlag` 在任意存档页面读取缺失入口；
- 首个 C367 不被 adapter 覆盖为存档页面，C367/C368 仍保持请求驱动；
- 家具、入口可见性与碰撞策略保持独立；
- `+0xC8` 表示显示状态，前置进度位于 `+0x80..+0x87`；
- 房间 tuple 保持原身份，资源查找使用限定映射；
- 战斗资源清单只登记实际存在或可重复派生的文件。

### 3.6.1 L7/L8二进制 patch 完整流程

**修改目标：** PE32客户端`game.exe`中小地图初始化函数`0x009000D0..0x00900156`。执行入口为自包含运行包的`Nanaimo.Adapter.exe --tools compatibility`，补丁配方内嵌在托管程序集；本文1.1节列出`--all`涵盖的其他指令与资源组件。

| 客户端资源状态 | `0x0090012F`完整指令 | `0x00900131` | 固定关闭章节 |
|---|---|---|---|
| 原始函数 | `C7 80 7C 0B 00 00 00 00 00 00` | `7C` | L7 |
| L7兼容布局 | `C7 80 80 0B 00 00 00 00 00 00` | `80` | L8 |
| 完整L7/L8资源 | `C7 80 84 0B 00 00 00 00 00 00` | `84` | L9 |

1. **准备。** 退出目标客户端及使用该目录的适配器／桥接进程；保存客户端和资源的完整备份，记录`game.exe`的SHA-256。选择独立覆盖输出目录，保持输入与输出根目录各自独立。
2. **资源预检。** L8目标要求`openNanaimo-l7-l8-resources.json`及其1328项安装资源逐项匹配大小与SHA-256；当前L7韩服怪物闭包、stage1 SSTG/PON兼容别名与L8资源使用同一清单。凭据摘要、路径唯一性及文件身份一起校验。L7兼容布局采用`B80`，完整L8资源采用`B84`。
3. **函数门禁。** 按PE32节表映射VA；完整函数必须匹配原始、L7或L8登记签名之一。输入匹配后仅调整该函数`0x00900131`的一字节位移；章节原生前置计算和其他函数内容按各自配方保留。
4. **只读预检。** 从项目根目录执行以下命令，核对结果中`planned_verification.all_pass`、操作站点及计划文件。

   ```powershell
   $Client = '<客户端根目录>'
   $Overlay = '<独立覆盖输出目录>'
   .\adapter_runtime\Nanaimo.Adapter.exe --tools compatibility --source-root $Client --output-root $Overlay --dungeon7 --dry-run
   if ($LASTEXITCODE -ne 0) { throw '客户端兼容预检失败' }
   ```

   L8资源可单独校验：

   ```powershell
   .\adapter_runtime\Nanaimo.Adapter.exe --tools verify-resources --client-root $Client --kind lumineos
   if ($LASTEXITCODE -ne 0) { throw 'L7/L8资源身份校验失败' }
   ```

5. **派生及应用。** 使用全新的覆盖输出目录，执行相同选项并添加`--apply`。重用已审阅的输出目录时添加`--overwrite`。`--dungeon7`同时处理道路、兼容别名和已登记图像迁移，具体范围见3.1–3.8节；`--all`按1.1节执行全部组件。

   ```powershell
   .\adapter_runtime\Nanaimo.Adapter.exe --tools compatibility --source-root $Client --output-root $Overlay --dungeon7 --apply
   if ($LASTEXITCODE -ne 0) { throw '客户端兼容应用失败' }
   ```

   工具先在内存派生全部文件并重复应用配方验证幂等，再写覆盖目录。应用前重新核对源字节并将原文件保存到`backups/<原SHA-256>/<相对路径>`；实际写入采用同目录临时文件原子替换。异常时按逆序恢复已修改文件，并以目标摘要保护并发编辑。
6. **结果校验。** 核对`nanaimo_compatibility_report.json`中的`verification.all_pass`、逐文件`apply_results`与输出摘要；重复只读预检应得到相同目标字节。核对完整函数及`0x00900131`目标值、村庄入口格点和全部L8资源身份。独立记录客户端地图显示和关卡操作验收。
7. **回滚。** 退出目标进程，将当前文件与该次报告的应用后SHA-256比较，确认仍属于本次应用结果；再从内容寻址备份逐文件恢复并核对原SHA-256。针对EXE优先恢复完整备份。单独撤销小地图项时，仍以完整登记函数为门禁，将`0x00900131`恢复到该次应用前的`7C`、`80`或`84`。资源和代码部署产生的事务按各自收据逆序恢复，角色数据库保持独立。

代码与资源整合部署入口`deploy_lumineos_release.py`同样在资源身份通过后应用该位点，默认执行预检，`--apply`执行事务；回滚使用该次输出的收据：

```powershell
python -B scripts/deploy_lumineos_release.py --client $Client --bundle '<已审核资源包>'
python -B scripts/deploy_lumineos_release.py --client $Client --bundle '<已审核资源包>' --apply
python -B scripts/deploy_lumineos_release.py --client $Client --rollback '<该次部署收据>'
```

每一步确认退出码为0后进入下一步。部署收据统一登记代码与资源事务，回滚以应用后摘要保护后续编辑。

### 3.7 场景衔接

page17与page18通过P03道路相连，action166进入地宫房间选择及创建界面。关卡使用对应SSTG、SMMO与PON资源；普通目标、Boss及结算共享所选难度。死亡、离开和通关后的返回路径使用所选布局的marker169：基础CN兼容布局返回格点`(25,6)`、像素`(400,96)`；韩服原生L7/L8布局使用返回格点`(10,15)`。再次进入时延续持久化关卡进度。

### 3.8 撤回补制美术并保留用户资源

地宫7入口、标题与建房背景的三项登记替代美术已从运行链撤回。以下SHA-256仅用于精确识别和安全迁移：

| 客户端相对文件 | 登记 SHA-256 |
|---|---|
| `images/Village_images/vill05_gate_ep07_restored.im3` | `B5A3B2E8C996DC666320A74732C1937E0DD0C648B96F70A662B33257FDC382A2` |
| `images/Village_images/vill05_guide_ru7_restored.im3` | `5E0885E380D6E50B15E391A858CD2558CE75FF1D244C7A14C7844472F9BE1D3E` |
| `images/interface_images/shootingsky_inter_image/dg_intro_hd0_ep23.im3` | `DB148EB9FBAD7F1CC85E3548AA58A827905925D63631387002F5ABEFE915FC83` |

`ep23` 是客户端按战斗资源 `ep22 + 1` 查找的背景名。迁移器仅移除SHA-256完全匹配的登记内容；其他同名内容保留，并在报告 `preserved_unknown` 中登记。迁移完成后由客户端现有资源决定对应背景显示。

对地图记录50018，派生器在识别到登记入口／标题时移除四个登记对象：底层入口 `(160,140)`、中层箭头 `(159,177)`、上层光柱 `(161,32)`、标题 `(164,18)`。其他摆放保持原状；重建同步维护记录长度、目录偏移、其余装饰及尾部，其他页面继续按既有P03规则处理。

`scripts/assets/dungeon7/` 保留三项精确识别夹具；生产迁移使用登记的SHA-256常量，安装路径执行资源撤回与小地图站点校验。

执行方式不变：`--dungeon7 --overwrite --apply` 将已知图像删除操作与 EXE、地图及别名写入纳入同一备份／失败恢复事务。所有被删除客户端字节保存于输出目录的内容寻址 `backups/`；重复操作幂等。仅生成 overlay 时，删除项出现在 `planned_removals` 和 `remove_on_apply` 中，普通文件复制无法表达删除，迁移应使用 `--apply`。重用含旧图像的输出目录要求 `--overwrite`，只清理哈希已知的旧 overlay 图像；未知 overlay 文件拒绝覆盖。

自动验证覆盖登记美术撤回、其他页面保留、入口／返村坐标、道路、内容保护、重复操作、失败恢复和小地图完整函数门禁。运行验收范围包括小地图状态、入口交互、建房界面及战斗／离场返村。

### 3.9 第五村页面的跟随宠物恢复

managed城镇的selector4路径在C367/C368入口边界完成可见状态，随后发布双向角色快照、当前PET附着和静止坐标，并初始化城镇资源同步。后续C36C及CB21保持同一完成状态。

### 安装

1. 退出目标游戏客户端和派生副本；配套程序更新同时要求适配器与worker处于退出状态。保存当前客户端、资源标记及运行清单，角色数据库和启动配置按各自事务保留。
2. 在工程根目录校验并解压资源包到全新目录：

```powershell
$Client = '<client-root>'
$Archive = (Resolve-Path 'resource-packs/nanaimo-korean-resource-kit.zip').Path
$Expected = ((Get-Content -LiteralPath ($Archive + '.sha256') -Raw).Trim() -split '\s+')[0]
if ((Get-FileHash -LiteralPath $Archive -Algorithm SHA256).Hash -ne $Expected) { throw '资源包摘要冲突' }
python -B scripts/package_korean_resource_kit.py verify --archive $Archive
if ($LASTEXITCODE -ne 0) { throw '资源包校验失败' }
$Kit = '<fresh-kit-directory>'
Expand-Archive -LiteralPath $Archive -DestinationPath $Kit
```

3. 资源安装器按全部基线、目标摘要和已登记旧标记预检；通过后保存原文件、旧标记和事务收据，并逐文件原子安装：

```powershell
python -B scripts/port_lumineos_resources.py apply --bundle "$Kit/l7-l8-bundle" --client $Client
if ($LASTEXITCODE -ne 0) { throw '资源安装失败，按事务收据处理' }
python -B scripts/port_lumineos_resources.py verify --client $Client
if ($LASTEXITCODE -ne 0) { throw '安装资源校验失败' }
```

4. 发布配套程序时使用成套运行目录，统一校验DCC7、HP、Boss、碰撞、计分、目标和掉落目录。整合部署入口`deploy_lumineos_release.py`默认预检，`--apply`执行资源、配套代码及小地图位点事务；它可作为上一步资源单独安装的整合替代入口：

```powershell
python -B scripts/deploy_lumineos_release.py --client $Client --bundle "$Kit/l7-l8-bundle"
if ($LASTEXITCODE -ne 0) { throw '整合部署预检失败' }
python -B scripts/deploy_lumineos_release.py --client $Client --bundle "$Kit/l7-l8-bundle" --apply
if ($LASTEXITCODE -ne 0) { throw '整合部署失败，保留事务收据' }
```

5. 小地图完整函数`0x009000D0..0x00900156`匹配登记签名后，在VA `0x00900131`将原`7C`或L7版`80`迁移为`84`，使固定关闭位移为`0xB84`，L7/L8继续使用原生前置条件。该目标以1328项资源完整校验为前提；基础L7兼容布局使用`80`／`0xB80`。同次全套客户端兼容按[安装、验证与恢复](../指南/客户端二进制补丁.md#df-12-011)生成、应用及校验，竞技五个位点按[结果页补丁统一流程](客户端兼容.md#结果页补丁统一流程)处理。
6. 验证`openNanaimo-l7-l8-resources.json`、资源全量摘要、兼容报告及三份发布清单，再通过启动器重新派生社交副本。重复安装校验幂等及stage1别名一致性。角色进度继续使用独立数据库。

### 恢复

1. 退出对应客户端；恢复配套程序时同时退出适配器及worker。核对当前文件与收据登记的安装后摘要，并校验备份摘要。
2. 整合部署使用`python -B scripts/deploy_lumineos_release.py --client $Client --rollback '<deployment-receipt>'`，由代码收据关联资源事务。
3. 单独资源事务使用`python -B scripts/port_lumineos_resources.py rollback --client $Client --receipt '<resource-receipt>'`。替换文件恢复原字节；本次新增且仍匹配安装摘要的文件按收据删除；旧资源标记随事务恢复。遇到后续编辑时保留现场并报告冲突。
4. 客户端EXE优先恢复该次完整备份；定点恢复以完整函数签名为门禁，将`0x00900131`还原为该次原值`7C`、`80`或`84`。竞技位点按[竞技场结果页配方](客户端兼容.md#df-12-012)逆序恢复。最后重新校验资源、程序、配方和派生副本的一致性。

资源包同时包含英雄龙与追加宠物配方、转换工具及`source-kr/`输入，PET按868→869→990合并。该模块的完整基线、所需资源、安装命令及恢复约定见[韩服资源说明](../指南/韩服L7-L8与宠物资源说明.md#5-随仓库资源包与安装步骤)；宠物表和散文件按其独立配方备份与校验。
