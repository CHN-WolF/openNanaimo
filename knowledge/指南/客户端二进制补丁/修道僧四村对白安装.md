| VA | 接受原值 | 目标与语义 |
|---|---|---|

| `0x6E33C0`，64字节 | `CC`×64或已登记第一关64字节窗口 | hd0、逻辑入口8～11时写入episode24～27及dg0，保持资源dg、寄存器、flags和ret4 |
| `0x527CCD`，5字节 | `E8F821EFFF` | `E82EBB1B00`，村庄更新调用对白控制器 |
| `0x72F20D`，5字节 | `E834F4CEFF` | `E8EE47FBFF`，来源匹配时以章节100初始化准备房，再映射挑战episode24～27 |
| `0x53CE10`，9字节 | `DB45E48B8554F8FFFF` | `E9EB701A0090909090`，按冻结来源恢复位置后继续原生角色创建 |
| `0x6E3800`，8,192字节 | `CC`×8,192 | 对白控制器、独立窗口虚表、48×96命中矩形、来源状态和GBK分页文案；完整目标字节由统一内嵌配方登记 |

64字节目标内容：

```text
9C528BC18B54240C899138E5010083B930E501000075218B914CE5010083EA0883FA03771383C218899148E50100C7814CE50100000000005A9DC20400CCCCCC
```

第一关窗口与当前窗口仅在VA `0x6E33E2`的入口上界立即数不同：`00`更新为`03`。安装器对整个64字节窗口执行已知身份校验。`0x72F0F0`的章节100分支执行本地选关；manager+0x1E548与+0x1E54C对应episode和dg，资源字段+0x1E534/+0x1E538供`0x66EC30`使用。Python与托管启动器共用精确位点配方。

对白控制器8,192字节目标窗口的SHA-256为`2F49189E78AC9D28723D60252759312369951BF50F78578AA390E0C9524664E0`。窗口虚表位于`0x6E4000`，来源状态位于`0x6E4040`，四村表位于`0x6E4100`，分页文案始于`0x6E4200`。每行最多36字节、132字节缓冲，每页三行；下一页确认更新窗口文本，最终确认进入对应准备房。窗口按`0x1F0`字节分配，调用原生`CVillageMessage`构造并登记窗口类型9。安装器接受精确原窗口或完整目标窗口，重复应用保持字节幂等。

#### 安装与核对

1. 退出客户端及目标运行程序，保留匹配的程序备份、数据库备份和资源事务收据，准备合法取得的源资源与目标客户端目录。
2. 生成并安装完整四关资源包，保存返回的资源收据：

```powershell
python -B scripts/prepare_monk_challenges.py build --source "<source-client>" --client "<client-root>" --output "<fresh-resource-bundle>"
python -B scripts/prepare_monk_challenges.py apply --bundle "<fresh-resource-bundle>" --client "<client-root>"
python -B scripts/prepare_monk_challenges.py verify --client "<client-root>"
```

3. 使用同一发布包的运行程序、DCC7、原生战斗目录和中文名牌基础，派生并安装四村场景事务：

```powershell
python -B scripts/prepare_monk_dialogue.py build --source "<source-client>" --client "<client-root>" --output "<fresh-entry-bundle>"
python -B scripts/prepare_monk_dialogue.py apply --bundle "<fresh-entry-bundle>" --client "<client-root>"
python -B scripts/prepare_monk_dialogue.py verify --client "<client-root>"
```

4. 派生兼容客户端，启动器沿用同一配方和场景目标身份：

```powershell
Nanaimo.Adapter.exe --tools compatibility --source-root "<client-root>" --output-root "<fresh-overlay>" --dungeon-state --dungeon7 --monk-dialogue --apply
Nanaimo.Adapter.exe --tools verify-resources --kind monk-dialogue --client-root "<client-root>"
Nanaimo.Adapter.exe --tools verify-resources --kind lumineos --client-root "<client-root>"
```

5. 核对源目录与启动overlay中的场景摘要、64字节选关位点、8,192字节对白窗口及四关资源身份。启动器根据`.openNanaimo-monk-dialogue.json`启用配方，联合校验11项场景资源和1,154项战斗资源。源码配方及托管内嵌配方随同一运行包发布；使用启动器重新派生各客户端副本。

#### 恢复

1. 退出客户端和目标运行程序；按兼容回执恢复客户端副本与原始程序摘要。
2. 按入口收据恢复场景原件，再按资源收据移除本次新增且摘要一致的文件；既有共享文件由保留清单核对：

```powershell
python -B scripts/prepare_monk_dialogue.py rollback --client "<client-root>" --receipt "<entry-receipt>"
python -B scripts/prepare_monk_challenges.py rollback --client "<client-root>" --receipt "<resource-receipt>"
```

3. 运行程序、战斗目录、发布清单和启动overlay按同一备份版本恢复；角色及独立挑战进度按数据库备份契约维护。战斗资源事务使用`.openNanaimo-monk-challenges.json`，四村场景事务使用`.openNanaimo-monk-dialogue.json`；恢复工具完整预检当前文件、备份摘要、清单覆盖和收据归属，再逆序恢复既有文件及本次新增文件。

当前资源、道路、程序位点及适配器构造验证通过。客户端可见触发、加载、战斗、结算、重试和回村属于实机验收范围。
### 场景资源完整清单

四村场景安装合同包含11项文件；大小和SHA-256由`manifest/monk_dialogue_resources.json`逐项维护。效果保留各村动画轨道，并统一引用独立角色图像、中文名牌和阴影。

|---|---:|---|

| `effs/village/openNanaimo_monk01.eff`至`openNanaimo_monk04.eff` | 每项1,688 | 分别由`vill01_npc_monk.eff`至`vill04_npc_monk.eff`派生，三处资源名称引用同步 |

| `effs/village/openNanaimo_monk_shadow.im3` | 1,342 | 共用阴影 |
| `effs/village/openNanaimo_monk_name.im3` | 1,418 | 13号中文名牌、45×19文字框与英文MONK |

场景基础继续使用`QS._D31`（31,136字节，SHA-256 `557B9C7290E730CF06C93EDBEC0B743A19574AFD85650BA8DEB9BA320CFD9B1F`）和`GS._D20`（40,624字节，SHA-256 `5C5D84F4D1075F208ACD221CE0F4724170182D747C38204D3369B7A12D31AF2D`）。对白配方从统一本地化目录生成GBK分页文本，关卡名和BOSS名与四关资源保持同一编号。

基础派生所需资源为`NPC._D39`、`effs/village/vill01_npc_monk.eff`、`vill01_npc_monk.im3`、`qz_village_npc_shadow_black.im3`和`vill_npc_monkname.im3`，配套本地中文字体；四村安装另外读取同目录`vill02_npc_monk.eff/im3`、`vill03_npc_monk.eff/im3`及`vill04_npc_monk.eff/im3`。四关战斗所需的完整源文件、转换和目标文件逐项归`manifest/monk_challenge_resources.json`。

共享包采用L7/L8父身份与四村场景叠加合同联合校验。发生摘要冲突时，按本次安装收据核对当前文件、安装前备份和父包清单；使用四村事务回执恢复后，再核对目标目录的配套资源：

```powershell
Nanaimo.Adapter.exe --tools verify-resources --kind lumineos --root "<client-root>" --client-root "<client-root>"
```

该命令应返回 `LUMINEOS_RESOURCES_PASS`；再用启动器兼容参数执行 `--dry-run`，检查退出码及 `verification.all_pass`。恢复操作和后续客户端兼容边界归[事务与恢复](../../工程/资源安装/事务与恢复.md#kb-09-026-14)。
