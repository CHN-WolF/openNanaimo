# 客户端二进制补丁

本文维护玩法兼容项的精确修改、安装与恢复契约。当前补丁由 `scripts/prepare_client_compatibility.py` 生成，运行程序使用同一配方的内嵌版本。

## 娱乐室房内最高纪录

准备房设置控制器支持同一房间的最高分与持有者更新。入口VA `0x00643500` 的原值 `55 8B EC 83 EC 08` 替换为 `E9 FB 00 0A 00 90`，转入VA `0x006E3600` 的256字节区域；区域原值为256个 `CC`，当前值由统一兼容配方生成。处理结束按原调用约定返回，保持栈、非易失寄存器和一次完成。

适用条件：普通44字节设置沿用原行为；80字节扩展要求DWORD+44=`0x31305245`、DWORD+48等于当前资料对象+0xD5C的房间身份、玩法为1至3、+79为NUL。通过后DWORD+52写最高分，+56起24字节写持有者，继续更新标题、密码和难度。格式或房间身份不匹配时，仅完成该项处理并保留既有资料。持久结算、榜首比较和成员轮次由适配器维护。

安装步骤：

1. 使用同一发布清单登记的适配器与兼容配方，结束使用待更新客户端副本的进程。
2. 执行 `Nanaimo.Adapter.exe --tools compatibility --source-root <client-root> --output-root <fresh-overlay> --dungeon-state --apply`，在全新目录生成兼容副本。
3. 工具同时校验6字节入口及256字节区域；接受登记的原值或当前值，重复安装保持幂等，其他内容按冲突处理。
4. 核对安装回执、原文件备份摘要及两处当前字节，再由启动器派生客户端副本。
5. 匹配版本的双客户端联合验收覆盖同房破纪录、持有者变化、下一局、普通设置和离房重建；构造与隔离执行结果统一见知识库[工程／验证状态](../knowledge/工程/验证状态.md)。

恢复步骤：

1. 选取本次安装回执对应的原文件备份，核验大小与SHA-256。
2. 校验当前6字节入口与256字节区域均符合登记配方。
3. 原子恢复入口 `55 8B EC 83 EC 08` 和区域256个 `CC`，保留其余兼容项，并再次逐位点校验。
4. 重新生成客户端副本，通过启动器启动；同一恢复回执保留完整文件身份。

## 玩家直接交易取消

C4BE由`0x7996F0`交易控制器分发。兼容配方按精确原值等长替换VA `0x799F9C..0x79A06D`的209字节，清理双方十槽对象、双方金币输入、等待标志及准备／确认状态，并恢复本方编辑。消息处理范围限定为C4BE取消分支，每个取消包只消费一次，交易房成员保持不变。字段和调用约定归知识库[玩家交易取消处理](../knowledge/业务/经济/玩家交易.md#kb-08-071)。

原值、新值由统一兼容配方生成，Python实现与托管内嵌配方逐字节一致，归既有`--dungeon-state`兼容组。209字节原值必须完整匹配后才允许生成新副本；运行中的客户端副本在退出后由启动器从更新后的game.exe重新派生。

安装步骤：

1. 结束使用旧客户端副本的进程，准备新的输出目录。
2. 执行`Nanaimo.Adapter.exe --tools compatibility --source-root <client-root> --output-root <fresh-overlay> --dungeon-state --apply`，生成兼容副本并应用交易取消修正。
3. 工具按内容摘要保存原game.exe，逐文件核对后原子安装，并逐一验证所有选定位点；209字节交易取消区域须显示原值匹配和新值匹配。
4. 通过启动器使用新game.exe派生客户端副本；同一交易房内取消后双方报价、金币输入、准备状态和确认状态均回到可重新编辑状态。

恢复步骤：

1. 从本次安装回执选择对应的原文件备份，核对备份摘要与当前文件登记身份。
2. 恢复前校验`0x799F9C..0x79A06D`仍为已登记的新值。
3. 原子还原209字节原值，保留其它兼容修正，并重新执行位点核验。
4. 重新生成客户端副本并通过启动器启动。

构造及隔离指令验证覆盖字节配方、16组空槽／十槽与ready／final状态和迁移一致性。双端取消后的画面状态及同房重新报价属于匹配发布版本的客户端联合验收项目；本节未提供该项实机验收记录，不能据此认定当前版本已完成画面验收。

## 200级字段、入口与显示

城镇C36A将低6位、6位称号、8位等级与12位UID组合。入口上限为200；物品详情表按0～200初始化，脚边等级在100～200使用三位布局并增加6像素间距。配方共8个位点：

| VA | 原字节 | 当前字节 | 职责 |
|---|---|---|---|
| `0x0053E138` | `C7 85 5C FF FF FF 7F 00 00 00` | `C7 85 5C FF FF FF 3F 00 00 00` | 称号mask为6位 |
| `0x0053E15A` | `C1 E9 0D` | `C1 E9 0C` | 等级右移12位 |
| `0x0053E15D` | `23 8D 5C FF FF FF` | `81 E1 FF 00 00 00` | 等级mask为8位 |
| `0x004E4660` | `CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC` | `3D C8 00 00 00 0F 8E 28 B8 01 00 E9 8F B7 01 00 CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC CC` | 32字节入口比较区，imm32比较200；成功至0x4FFE93，否则至0x4FFDFF |
| `0x004FFDF6` | `83 F8 63 0F 8E 94 00 00 00` | `E9 65 48 FE FF 90 90 90 90` | 入口跳转到0x4E4660并以4字节NOP补齐 |
| `0x0094F0A9` | `C7 45 E4 63 00 00 00` | `C7 45 E4 C8 00 00 00` | 物品成长表初始化上限200，覆盖0～200键 |
| `0x006DBA10` | `83 F8 64 75 0B` | `83 F8 64 7C 0B` | 等级≥100采用三位宽度 |
| `0x006DBA18` | `83 C1 0F` | `83 C1 15` | 三位等级与名字间距由15改为21像素 |

`0x004E4660`为独立32字节区，与既有`0x004E4600`／`0x004E4620`兼容区分别维护。相对跳转以指令末地址计算，整数200使用imm32编码。位点原值与目标值由`scripts/level200_compat.py::patch_sites()`统一提供；`restore()`按相反顺序恢复精确原值，遇到第三方字节冲突时终止。

GUI核对兼容报告中的城镇及入口操作，再由`gui_launcher/level200_client_check.ps1`与`level200_client_sites.json`核对全部8项PE字节；独立连接器执行同一检查。当前程序使用64位人物累计及CurveVersion3，客户端以级内u32三元组显示，数据字段见`level200/internal-layout.md`。

## 娱乐室创建模式

创建确认后直接沿用客户端原生的多人房间流程，房间模式初始化为多人（最多6人）。适配器统一处理房间状态、等待、开始、计分、结束和宠物经验结算。

| 修改点 | 当前契约 |
|---|---|
| 创建模式赋值 | VA `0x0077744D` 保持原6字节 `66 C7 45 E8 C8 00`，直接走客户端原生多人初始化 |
| 选择框兼容位点 | 原生多人入口；VA `0x006E3240` 保持连续`CC`区域，消息框调用链保持原始布局 |
| 兼容配方 | `--dungeon-state` 将已登记的旧选择框编码迁移为原生多人入口；娱乐室资源和适配器房间流程保持原有契约 |

## 娱乐室幸运卡结果显示

本节维护特殊卡代码的结果显示兼容契约。当前娱乐室发奖使用基础卡目录和原生预览；发奖与去重规则见知识库[娱乐奖励](../knowledge/业务/娱乐/奖励.md#kb-07-022-1)，目标分数与计分规则见[娱乐对局](../knowledge/业务/娱乐/对局.md#kb-07-022-2)，计分载体见[娱乐对局字段](../knowledge/业务/娱乐/对局.md#kb-08-073-4)。

TIME UP后CF86的幸运卡22000011..18由特殊卡目录消费，使用原通用图标和特殊卡记录+245的卡名图片路径，普通／SP／活动卡保持原生查询。名称返回值交给图片加载器，记录+8保存中文文本，+245保存图片路径。特殊卡的大图预览槽归零，三个排名奖励字段及实际入库保留原卡号。

精确配方由`scripts/entertainment_result_compat.py::patch_sites()`生成，归`--dungeon-state`组，并同步内嵌配方：

| 位点 | 原值与当前职责 |
|---|---|
| `0x006E3400` | 192字节原`CC`区，当前存分类／名称／预览包装函数 |
| `0x0064A423` | 原13字节`81 7D 10 80 F0 FA 02 0F 86 AC 00 00 00`；开放幸运卡到`64A430`，其余保留原50000000判断 |
| `0x0064AC90` | 原5字节`E8 E1 04 DD FF`；幸运卡经特殊目录记录+245取卡名图片路径，其余保留`41B176` |
| `0x0064401F` | 原5字节`E8 07 40 DC FF`；幸运卡大图参数为0，其余保留`64B060` |

192字节代码区接受原CC、已登记的旧+8配方或当前+245配方，统一迁移至+245图片路径编码；其他字节按冲突处理。四处位点共保护215字节，实际变化范围由精确配方逐字节核对。专项覆盖八种资源记录、目录分流、图片路径与扩展名解析、预览清理、栈、旧版迁移、幂等和冲突保护，验证层级为隔离x86执行与资源构造。

安装与恢复按下文“结果页补丁统一流程”执行；娱乐室选择框迁移与幸运卡显示兼容项均随`--dungeon-state`应用。恢复时使用该次安装的原文件，或在核对四处当前值后按配方逆序恢复原值；角色与奖励事务继续使用各自持久化契约。

## 组队与超级Boss结算入口

两个战斗控制分支共同等待完整结算数据，再进入结果页面。结果排序先完成，页面状态随后切换；新的确认操作从结果页建立独立输入边界。

| 修改点 | 当前契约 |
|---|---|
| 普通控制分支 | VA `0x0066CD71`，`74 1A`改为`EB 1A`，转入当前战斗更新的后续分支 |
| 组队控制分支 | VA `0x0066CD45`，`74 1A`改为`EB 1A`，转入当前战斗更新的后续分支 |
| 完成数据后的入口 | VA `0x006FADE9`，原`E8 E3 71 D1 FF`，改为调用VA `0x006E3180` |
| 结果发布函数 | VA `0x006E3180`，长度96字节；兼容连续`CC`原区域及已登记的单控制器版本，安装双控制器编码 |
| 模式与页面范围 | 管理器`BYTE+3`取0或1；`DWORD+0x10F0`取4或6；活动页4通过`0x006692E0`设置为结果页6 |
| 排序与输入 | 先调用`0x00411FD1`完成排序；键盘当前区`+0x0C`复制到`+0x10C`，长度256；鼠标当前区`+0x210`复制到`+0x220`，长度16；保留寄存器、标志、返回值和栈 |
| 最终总分排序入口 | VA `0x00762230`，6字节评级分支改为进入总分比较区；原字节`0F 8D A1 00 00 00`，目标字节`E9 A2 00 00 00 90` |
| 最终总分比较区 | VA `0x007622D7`，原154字节按精确配方等长替换；控制器行步长`0xAC`，`+0x4BC`最终总分降序、同分`+0x448`角色UID升序，保留评级值；保持`+0x4E8`就绪门控和原生交换／绘制路径 |
| 精确配方 | `scripts/dungeon_result_compat.py`中的`encodings()`、`sorting_sites()`与迁移函数；两个新增排序位点随`--dungeon-state`派生，既有客户端及多开social派生副本均须重新应用／核验 |

## 连续挑战的旧战斗状态清理

结果页直接发布后，旧战斗控制器可能仍处于退出状态；若留到下一关开场才完成清理，会关闭新场景的运行开关。只在适配器已确认续关的普通CF8C结果重载路径调用原生控制器reset，然后沿用原有重载，角色与资源由原加载链维护。

| 修改点 | 当前契约 |
|---|---|
| CF8C重载尾调用 | VA `0x006FBF5C`，原5字节 `E8 1B 5B D1 FF`，调用包装区 |
| 包装区 | VA `0x006E3340`，原96字节连续`CC`；实际编码和填充由配方生成 |
| 作用域 | 原参数state7；管理器BYTE+3为0／1、DWORD+0x10F0为6；battle单例槽`0xD72FA8`非空 |
| 调用与保护 | 原生`0x746C60`复位旧battle；保存全部通用寄存器／flags，再尾跳原`0x411A7C`；原this、参数、返回地址及ret4约定不变 |
| 保持项 | world运行位、actor、HP/MP/P、结果行及CF8C/48、CF71、CF80沿用原合同；其它作用域保持原调用 |
| 精确配方及回归 | `scripts/dungeon_result_compat.py::continuation_sites()`；`scripts/test_dungeon_continuation_client.py` |

## 配套运行包合同

城镇角色初始构造、称号增量及广播统一使用称号`0x3F << 6`、等级`0xFF << 12`，保留低6位和UID位20～31；本页三处城镇读取位点采用相同布局。连续挑战的CF8C包装负责旧战斗控制器复位，适配器按CF99成员状态管理CF6D，并合并重入产生的两轮资料：首轮完整初始化，第二轮复用本人坐标并更新资源、队友及准备状态。

配套校验覆盖等级127／128／199／200／201、称号0～255归一化、两种CF70到达顺序以及成员／房间生命周期。下述预检、派生、配方同步、安装一致性和恢复步骤共同构成客户端二进制补丁的完整应用流程。

## 安装、验证与恢复

### 1. 预检与生成

1. 退出目标客户端，确定源文件、独立输出目录和配套程序版本。记录源文件大小与SHA-256；经验曲线切换同时建立匹配的数据备份。
2. 解析PE节表，将本页VA映射到有文件内容的偏移，检查位点范围及代码区重叠。各位点须匹配精确原值、登记旧版或当前值；冲突终止生成。
3. 结果发布函数接受原96字节`CC`及`encodings(legacy=True)`定义的单控制器版本，统一迁移到mode0／1版本。其它新增位点按各自原值／当前值匹配；已有兼容项由完整配方统一维护。
4. 以独立目录派生客户端：

```powershell
python -B scripts/prepare_client_compatibility.py --source-root "<client-root>" --output-root "<overlay-root>" --dungeon-state --dry-run
python -B scripts/prepare_client_compatibility.py --source-root "<client-root>" --output-root "<overlay-root>" --dungeon-state
```

该组同时处理既有地宫状态兼容项。需要全套资源与客户端兼容时使用`--all`；其资源合同见《完整适配器与客户端兼容说明》。派生工具按配方写入代码区和入口，保持文件长度及配方范围外字节。

### 2. 配方与安装一致性

1. 配方更新后执行`python -B scripts/generate_managed_compatibility_recipe.py`生成`managed-host/Resources/client-compatibility.json`，按《构建与验证》重新构建运行程序。
2. 托管内嵌配方、Python配方及启动器位点目录逐项一致。对派生文件重新核对全部位点，并重复应用检查字节幂等。
3. 安装由兼容工具的`--apply`或启动器兼容入口执行。目标文件保持退出状态；安装按内容摘要建立本机备份，记录原／新文件身份，逐文件确认后替换。
4. 排序配方包含`dungeon_result_score_order_entry`（6字节）与`dungeon_result_score_order_compare`（154字节）两项，均由`sorting_sites()`生成精确原值／目标值。比较区使用32位无符号总分，按角色UID稳定处理同分，剩余区域以NOP填充。逐项确认原生交换`0x00762371`、保持`0x0076240D`及就绪门控的分支目标；这160字节范围内实际更新137字节。
5. 多开social派生副本通过当前启动器的source rollover同步源文件身份、兼容配方和槽位注册摘要；每个副本分别核对上述排序位点及完整兼容报告。
6. 安装后验证目标PE全部位点、文件长度、兼容报告和启动器检查。托管程序、worker、启动器及发布清单同步使用同一配套版本。

### 3. 专项校验

应用后执行以下配方与隔离执行检查：

```powershell
python -B scripts/test_dungeon_experience_compat.py
python -B scripts/test_live_dungeon_experience.py
```

### 4. 恢复

1. 退出对应客户端；涉及程序或经验曲线恢复时，同时停止匹配适配器与worker并备份当前数据。
